# 0.107.0 对照 1.12.2 源码审查报告

日期：2026-10-25。性质：代码审查，不是修复交付或游戏验收。

## 结论与证据边界

当前版本存在阻断发布的问题：配方资源结算会部分扣料/部分出货，工厂恢复会丢在途状态，ME 流体输入会删除资源，供应器推料有复制资源的路径，自动搭建存在确定的运行时异常，供应器也尚未正确注册真实 AE2 合成服务。

本轮列出 **27 项问题**。其中 **12 个异常现象已通过当前编译源码的专项 Java 探针复现**；其余以源码控制流、旧版真实消费者和本地依赖的字节码作为证据。这里的“复现”指离线调用真实类/方法，不能替代整台 Minecraft、真实 AE2 网络或渲染实测。没有把文档中的“完成”当作行为正确的证据，也没有把已明确暂缓的功能算作缺陷。

覆盖：普通控制器与工厂结算、需求筛选/并行、NBT 恢复、AE2 总线/供应器及消息处理、自动搭建、投影、适配器、Mekanism 修改器分派、构建配置、资源 JSON 和现有复现器。项目共有 241 个 Java 文件；本轮对这些关键路径做深读与旧版对照，**不声称逐行穷尽全部 241 个文件或找全所有缺陷**。未做进游戏、专用服务器启动、全部可选依赖组合或性能负载测试。

## 必须优先处理的问题

### 01 [P1] 整条配方没有共享资源预留，检查通过后仍会扣料失败、丢产物

**位置**：`recipe/MachineRecipe.java` 的 `canStart/start/canFinish/finish`；`recipe/IngredientIo.java:127` 附近的 `simulateInsertAll`；`block/MachineControllerBlockEntity.java:821,883,906`；`factory/FactoryEngine.java:447,470`。

每个需求独立检查同一份未改变的库存/空间，没有把前一个需求模拟占用的资源计入后一个需求。结算则逐需求真正执行，失败时没有事务回滚；控制器还忽略 `tick()` 和 `finish()` 的 false。

**已复现**：配方含两条各需 1 煤的输入、库存只有 1 煤：`canStart=true`，随后 `start=false`，煤已变成 0。配方输出钻石和绿宝石、输出仓只有一个空槽：`canFinish=true`，随后 `finish=false`，只得到钻石；正式控制器仍清空本次合成状态。

**旧版依据**：`old: hellfirepvp/modularmachinery/common/crafting/helper/RecipeCraftingContext.java:103,434-447,518-524,565-576` 复用同类组件副本进行模拟，而非每条需求重新面对原始库存。修复应围绕整次资源规划和提交，不能只在 false 后重试，以免重复结算前面已输出的产物。

### 02 [P1] 注册表配方残留的并行数会干扰其他控制器与下一次开工

**位置**：`block/MachineControllerBlockEntity.java:1276-1281,1636-1645`；`factory/FactoryEngine.java:277-291`；`recipe/MachineRecipe.java` 的 `setParallelism`。

配方对象从全局 RecipeManager 直接取出，并把运行态并行数写进需求。搜索候选时直接 `canStart`，却没有先恢复单份检查；重设并行数发生在已经选中配方之后。因此一台机器运行了 64 并行后，另一台只有单份材料、甚至没有并行能力的机器也会按 64 份检查而停机。上一轮自己跑完高并行后也会遇到同样问题。

**已复现**：同一真实配方对 1 煤库存，设并行 1 时能启动；设并行 64 后，相同查询失败。

**旧版依据**：`old: .../crafting/helper/RecipeCraftingContext.java:149-157` 为每个 context 深拷贝需求；并行数写在该 context 的需求上。应隔离结算状态，或让所有候选检查显式使用自己的状态。

### 03 [P1] 计算最大并行时没有应用 selector-tag，合法结构可能永远开不了工

**位置**：`recipe/MachineRecipe.java` 的 `parallelism` 循环，调用 `requirement.parallelLimit(ports, ...)`；对照同类中 `canSatisfy/applyPhase` 会先调用 `visiblePorts`。

最大并行按所有标签的仓口合计，正式开工却仅使用目标标签。**已复现**：`line_0` 只有 1 煤、`line_1` 有 63 煤、需求指定 `line_0`，计算得到 64 并行，随后开工失败；正确结果应为 1。当前流程没有降为可行并行重试。

**旧版依据**：`old: .../crafting/helper/RecipeCraftingContext.java:212-232,423-447` 先得到带标签筛选的 RequirementComponents，再计算并行。

### 04 [P2] 未写 selector-tag 的需求被错误限定为只能使用无标签端口

**位置**：`machine/HatchCollection.java:259`；`recipe/MachineRequirement.java` 的 `visiblePorts`。

`withTag(null)` 仅保留 UNTAGGED；旧版的语义是未指定标签就不加标签过滤。**已复现**：带 `line_0` 标签的输入仓装着煤，无标签煤需求仍答不能启动。给机器部件添加标签后，本来不需要指定部件的普通配方会失效。

**旧版依据**：`old: .../crafting/helper/RecipeCraftingContext.java:221-230`，`tag != null` 时比较，`else` 接纳全部有效组件。若确实要保留新规则，应作为明确的不兼容决定交给所有者，不能声称与旧版一致。

### 05 [P1] 工厂在正常区块加载时会丢掉所有在途配方

**位置**：`block/MachineControllerBlockEntity.java:2113-2123,2458`；`factory/FactoryEngine.java:679-687`。

`load()` 立即恢复线程，配方解析 lambda 在 `this.level == null` 时返回 null，恢复器随后丢弃该在途合成。正常 `BlockEntity.loadStatic` 在 `setLevel` 之前调用 `load`，所以这不是罕见异常分支；后续 `onLoad` 没有延迟重试恢复。输入早已支付，重新加载后没有产物可拿。

**证据**：本地 1.20.1 `BlockEntity/LevelChunk` 的字节码已保存到 `mc-be-lifecycle-javap.txt`，可见 `loadStatic → load → setLevel` 顺序。本项未启动实际世界复验。

**旧版依据**：`old: .../tiles/TileFactoryController.java:596-613` 与 `old: .../machine/factory/FactoryRecipeThread.java` 的 `deserialize/deserializeActiveRecipe` 恢复活动配方，没有这条新 `Level` 空引用门槛。应暂存 NBT，到世界、机器和配方注册表可用时恢复。

### 06 [P1] 工厂线程保存时漏掉并行数，恢复固定变成 1

**位置**：`factory/FactoryThread.java:279-307`；`factory/FactoryEngine.java:691`。

保存只有配方 id、进度、组号；恢复硬编码 `new ActiveCraft(recipe, 1, ...)`。即使修好了问题 05，已支付 32 份原料的在途合成也只剩 1 份产出和单份后续消耗。

**已复现**：真实线程 32 并行，经过 `save → FactoryEngine.load` 后并行数为 1。

**旧版依据**：`old: .../machine/factory/FactoryRecipeThread.java` 的 `serialize` 保存完整 ActiveMachineRecipe；`old: .../crafting/ActiveMachineRecipe.java:51-63,151-157` 明确读写 `parallelism`。

### 07 [P1] 样板供应器没有注册 ICraftingProvider 节点服务，真实 AE2 网络看不到样板

**位置**：`compat/ae2/MePatternProviderBlockEntity.java:108-132`。

实现 Java 接口不等于给 AE2 节点注册服务。构造链只有 flags、耗电、位置和贴图，没有 `.addService(ICraftingProvider.class, this)`。`requestUpdate` 只能刷新已存在的供应者，不能补注册。

**API 证据**：AE2 `NetworkCraftingProviders.addProvider(IGridNode)` 只调用 `node.getService(ICraftingProvider.class)`，null 就直接返回；`GridNode.getService` 只读 services map，不回退检查 owner。字节码见 `ae2-services-javap.txt`。

**旧版依据**：`old: github/kasuminova/mmce/common/tile/MEPatternProvider.java:219-225` 使用旧 AE2 的 `provideCrafting/addCraftingOption`；新 API 不能只照搬“类实现接口”的表面形状。此项解释了为什么 GUI 放入成功不能证明端到端可用。

### 08 [P1] 样板部分推料后返回 false，会使 AE2 退回并再次使用已落地的材料

**位置**：`compat/ae2/MePatternProviderBlockEntity.java:299-328,354-355`。

代码会先把部分材料真的放进机器，再因剩余材料放不下而返回 false，没有撤销写入，也没有减少 inputHolder。AE2 把 false 当作这一批未被接收，转试其他供应器或把 inputHolder 回注 CPU 库存。同一材料因此同时留在机器和 AE2 任务库存，形成复制资源路径。

**API 证据**：本地 AE2 `CraftingCpuLogic.executeCrafting` 字节码 offset 226 调用 pushPattern；false 分支最终调用 `CraftingCpuHelper.reinjectPatternInputs`，见 `ae2-cpu-javap.txt`。

**旧版依据**：`old: github/kasuminova/mmce/common/tile/MEPatternProvider.java:234-272` 先选无限缓冲，之后整批接收返回 true；`InfItemFluidHandler.java:273-303` 的 appendItem 会扩展缓冲，没有“部分插入再 false”的语义。新版注释称此行为与旧版一致，事实不成立。此项是修复问题 07 后会暴露的后续缺陷。

### 09 [P1] 流体样板分摊到多个输入仓时，后续仓仍收到原始总量

**位置**：`compat/ae2/MePatternProviderBlockEntity.java:339-351`。

循环更新 `remaining`，但模拟填充始终传原始 `stack`。例如样板要求 1000 mB，第一仓接收 600，第二仓能收 1000：代码总共放入 1600，`remaining` 成为 -600，并视作成功。执行 fill 的实际返回值也被忽略。

**旧版依据**：旧供应器经无限流体缓冲整批接收（上一项旧版位置），不做这条分仓循环。新循环必须每次只提供剩余量，并按执行返回值结账。源码算术确认，未连真实 AE2 复现。

### 10 [P1] ME 流体输入在罐池没有空间时仍从网络真抽取，装不下的流体被删除

**位置**：`block/MeFluidBusLogic.java:48-55,118-132`；`compat/ae2/MeItemBusBlockEntity.java:481-487`。

抽取量只取决于目标减当前量，没有模拟罐池的实际接收能力。网络 extraction 使用 MODULATE；pour 把无法容纳的剩余量静默丢掉，也没有返还网络。

**已复现**：9 个罐装满共 72000 mB 熔岩，配置另要 1000 mB 水；网络减少 1000，罐池水量仍为 0。保留熔岩标记以排除“未标记清退”干扰。

**旧版依据**：`old: github/kasuminova/mmce/common/tile/MEFluidInputBus.java` 的 `tickingRequest` 按每槽 `capacity - invStack.getStackSize()` 抽取，并把返回栈写回对应槽。共享罐池是新版选择，但仍须保证资源守恒。

### 11 [P1] 供应器按附近第一个成型控制器找主机，会把材料送进别人的机器

**位置**：`compat/ae2/MePatternProviderBlockEntity.java:365-382`。

±8 格三重循环只检查控制器已成型，不检查供应器是否属于其有效结构，也不核对样板归属。孤立供应器也可以往附近机器塞料；两台机器相邻时取的是坐标扫描顺序，超过 8 格的大机器又找不到自己的控制器。

**旧版依据**：旧 `MEPatternProvider` 作为 MachineComponent 暴露自己的库存，由控制器从匹配结构中收集；没有这个“诊断搜索半径决定机器归属”的流程。新版 `MachineControllerBlockEntity.java:1663-1683` 自身也以 effectivePattern 位置收集端口。应使用结构成员绑定，而非邻近猜测。本项为静态确认。

### 12 [P1] 生存破坏样板供应器时没有保存/掉落样板，供应器自身也缺掉落表

**位置**：`compat/ae2/MePatternProviderBlock.java` 全类；`block/ModBlocks.java:423-427`；资源 `data/` 的 loot tables；`block/GeneratedLootTablePack.java` 生成范围。

供应器改成真实物品槽后，没有对应 onRemove/getDrops 或物品 NBT 迁移；注册的是普通 BlockItem。资源中也没有 `blocks/me_pattern_provider` 掉落表，生成掉落包只覆盖控制器。生存拆除会移除 BE，编码样板没有转移落点，供应器方块也没有正常自掉落表。

**旧版依据**：`old: github/kasuminova/mmce/common/block/appeng/BlockMEPatternProvider.java` 的 `breakBlock` 把 `writeProviderNBT` 放进掉落物 `patternProvider`，`onBlockPlacedBy` 读回。应至少完整掉出样板和方块，或复制旧版“携带内容的方块物品”语义。未在真实世界破坏复验。

### 13 [P1] 供应器写入消息没有菜单/距离校验，客户端可操作任意已加载供应器

**位置**：`network/MePatternPacket.java:60-87`；`network/MePatternProviderActionPacket.java:48-55`。

只按客户端提供的坐标找 BE，不要求当前打开的是对应供应器菜单，不校验容器 id、距离、区块加载状态。取出分支也不要求 carried 为空，直接覆盖 carried。因此自定义客户端可以远程取走样板、改模式；异常点击时还能删除光标上的已有物品。

**旧版依据**：`old: github/kasuminova/mmce/common/network/PktMEPatternProviderAction.java:36-45` 先验证玩家当前 openContainer 是 ContainerMEPatternProvider，再从菜单获得 owner；旧样板槽交互走受限真实容器。新包把目标坐标交给客户端决定，扩大了操作权限。服务端应从已验证菜单取得 provider，并验证移动前提。

### 17 [P1] 生存自动搭建必经不可变列表的 remove，第一格就可能令服务端 tick 抛异常

**位置**：`common/assembly/MachineAssembly.java:98,114-120,130,150`。

start 把 `List.copyOf(working)` 存为 remaining；tickPlace 对它的迭代器调用 remove。成功放置、不可替换、缺料三条路径最终都会尝试删除，所以任何非空生存搭建任务都会遇到 UnsupportedOperationException；成功放置路径已先扣料和改世界。创造模式走另一条循环，不能用创造搭建成功证明生存正常。

**已复现**：按 start 的同一构造方式创建真实 MachineAssembly，取 remaining 的迭代器并删除，得到 UnsupportedOperationException。离线没有调用需要真实 ServerLevel 的放置阶段。

**旧版依据**：`old: ink/ikx/mmce/common/utils/StructureIngredient.java:50` 显式创建可变 ArrayList；`old: ink/ikx/mmce/common/assembly/MachineAssembly.java:410-464` 在可变清单上 remove。

### 19 [P1] 投影仪的普通右键入口会先被控制器开窗吞掉

**位置**：`item/MachineProjectorItem.java:43-54`；`block/MachineControllerBlock.java:111-127`；`network/ProjectorRequestPacket.java:65-67`。

投影逻辑放在 Item.useOn，但控制器 Block.use 对普通右键无条件返回成功并开窗；通常方块交互先于物品 useOn，导致文档描述的“手持投影仪右键控制器”进入 GUI。物品没有 onItemUseFirst 或专用事件接线。

即使通过潜行等方式绕过方块交互，物品与请求端仍只接受已经成型的控制器；普通无额外 modifier 的完整结构会立刻匹配并清除投影，未完成结构却无法投影。这使建造指引的主要使用场景不可达。

**旧版依据**：`old: hellfirepvp/modularmachinery/client/util/BlockArrayPreviewRenderHelper.java:98-127` 可把已选结构附着到控制器或普通方块旁边，并不要求目标已经成型。此项源码/交互顺序确认，未进游戏操作。应先恢复完整的“选机器 → 为未完成结构放置投影”的交互链。

### 21 [P1] 机器配方适配器重建需求时丢 selector-tag

**位置**：`recipe/adapter/DynamicMachineAdapter.java:94-145`。

网络往返已经复制出带标签的需求，但 item/fluid/energy 分支又创建了全新对象，返回前没有复制基类元数据。带分段标签的父机器配方被适配后成为无标签需求，无法再指向原本的仓口。`parallelize-unaffected` 也同时丢失，网络本身另有问题 22。

**已复现**：真实 copyModified 对 `selector-tag=line_0` 的输入返回 `selector=null`。

**旧版依据**：`old: .../crafting/MachineRecipe.java:261-262` 使用 `deepCopyModified(...).postDeepCopy(requirement)`；`old: .../crafting/helper/ComponentRequirement.java:194-195,458-462` 明确恢复标签和 unaffected。需要在最终返回对象上复制基类字段，不能只证明中间往返保真。

### 23 [P1] 适配器生成 id 使用全局流水号，和控制器保存配方 id 的事实冲突

**位置**：`recipe/adapter/RecipeAdapterRegistry.java` 的 `generateAll/nextId`；`recipe/adapter/AdapterMinecraftFurnace.java` 的生成循环；`block/MachineControllerBlockEntity.java:1535-1540,2403-2404`；`factory/FactoryThread.java:286`。

生成 id 只有 adapter、目标机器和全轮递增序号，没有源配方 id。增加/删除一条较早遍历的熔炼配方、改变声明顺序，就会让某个旧 id 指向另一条生成配方。控制器和工厂却真实保存并按 id 恢复在途配方，可能把已付款的 A 合成恢复为 B，导致错产物、错资源或进度失配。源码注释“没有东西持久化它”与实际消费端冲突。

**旧版依据**：`old: .../crafting/adapter/DynamicMachineRecipeAdapter.java:51-57` 的派生名保留父配方 res.getPath；熔炉适配器 `AdapterMinecraftFurnace.java:64` 名称也包含输入和输出身份。即使旧实现本身并非完美稳定，新版也不应把源身份完全删掉。应从声明 id、源配方 id、目标机器 id 派生稳定 id，并定义 reload 中在途配方变化策略。本项静态确认，未改数据包触发存档复验。

### 14 [P2] 供应器首次开窗没有同步已有样板，重登后会看到空面板

**位置**：`compat/ae2/MePatternProviderBlockEntity.java:436-462` 附近的 getUpdatePacket/onDataPacket（未覆写 getUpdateTag）；`menu/MePatternProviderMenu.java:36-41`；`network/MePatternPacket.java:91`。

BE 继承的 getUpdateTag 默认不携带 patterns，初始区块同步也没有样板；菜单构造从客户端空 BE 复制，而专用列表同步只在点击修改/模式变更后发送，开窗时没有发送。现有“写入后更新客户端 BE 镜像”只能帮助同一客户端本次会话重开，不能解决重登或其他观察者首次开窗。

**旧版依据**：旧 `ContainerMEPatternProvider` 使用真实同步槽和专用供应器状态包。新版需要初始菜单快照或正确的 BE update tag。此前注释把空 tag 归因于原版移除语义，没有处理当前类根本没提供同步 tag 的根因。本项静态确认。

### 15 [P2] 样板镜像和 NBT 读取压缩空格，样板槽号不保真

**位置**：`compat/ae2/MePatternProviderBlockEntity.java:398-402,481-490`。

保存按列表逐项写，读取却只添加非空栈；客户端 BE 镜像同样过滤空项。把样板放在第 10 格、前面空着，重载后就被挤到第 1 格。同步菜单短期保留原槽号，但关闭后新菜单从已压缩的 BE 初始化，于是显示位置与服务端实际格号可不一致，点击会操作别的格子。

**旧版依据**：旧供应器使用固定 PATTERNS 槽数的库存序列化 `patterns.readFromNBT/writeToNBT`，槽位身份保留。需要固定 36 槽或显式保存索引。本项静态确认。

### 16 [P2] 供应器工作锁跨重载恢复不完整

**位置**：`compat/ae2/MePatternProviderBlockEntity.java:127-133,214-216,243-253,473-485,504-516`。

合成锁从 NBT 恢复 `lockActive=true`，但新 BE 没有加入 ACTIVE_LOCKS；完成事件只遍历该集合，因此重载后的锁无法被完成事件释放。强化阻挡读取 lock_active，但保存只在 CRAFTING_LOCK_MODE 写该键，强化模式重载后又总是恢复为未锁，允许混入不同样板。两种模式是相反方向的错误。

**旧版依据**：`old: github/kasuminova/mmce/common/tile/MEPatternProvider.java:513-539,565-580` 保存 machineCompleted、模式和 currentPatternIdx，运行中的机器关联走原组件链。直推架构可以不同，但存档恢复必须重新建立事件接收关系。本项静态确认。

### 18 [P2] 自动搭建的材料规划没有兑现候选选择，也没有扣除已搭好的部分

**位置**：`common/assembly/AssemblyHandler.java:126-127`；`common/assembly/AssemblyIngredient.java:36-64`；`common/assembly/MachineAssembly.java:195-218`。

扫描只接收结构定义，没有世界信息，已正确放置的方块也进入材料需求；need-all-blocks 开启时，玩家还要额外带齐整机材料才能补最后一格。bindCandidates/consumeItem 则只读 candidates.get(0)，注释所称“逐格选候选”没有实际实现。

**已复现候选问题**：一格接受石头或圆石，背包有圆石，真实 bindCandidates 仍把它列为缺料。

**旧版依据**：`old: .../util/BlockArray.java:245-253` 只收世界里尚未匹配的位置；`old: ink/ikx/mmce/common/assembly/MachineAssembly.java:103-123` 遍历候选并把选中的候选绑定到执行清单。修复不可变列表后，这仍是独立功能缺陷。

### 20 [P2] 幽灵预览把所有负相对 Y 层当作未激活

**位置**：`client/preview/WorldGhostPreview.java:77,212,264-270`。

renderedLayer 是相对控制器坐标，却用 `< 0` 判断无需渲染。控制器下方本来就允许 Y=-1、-2 等结构层；updateLayers 会选中这些真实负层，渲染入口却全部退出，最低缺失层一直补不出来。应把“无层”与合法整数坐标分开表示。

**旧版依据**：旧 `BlockArrayPreviewRenderHelper.java:247-251,335-344` 根据实际最低层选层，并只比较“本格层号是否等于选中层”，没有把负层号全部跳过的守卫。新版的 `< 0` 判断引入了这个限制。源码确认，未做画面实测。

### 22 [P2] parallelize-unaffected 没进入需求网络协议

**位置**：`recipe/MachineRequirementParser.java:184-214`。

JSON 正确设置了该字段，网络 write/read 只覆盖类型正文和 selector-tag。**已复现**：普通 item 需求 unaffected=true，经真实编解码后变成 false。客户端显示状态不保真；适配器把网络往返当深拷贝通道，因此连服务端派生配方也丢该语义。

**旧版依据**：`old: .../crafting/helper/ComponentRequirement.java:458-462,568-572` 的 postDeepCopy 保留该位。需要补协议字段及读写兼容约束，再处理问题 21 的最终对象重建。

### 24 [P2] 随机范围物品产出忽略数量修改器

**位置**：`recipe/ItemRequirement.java:309-320`。

检查和并行计算用 modifiedAmount，实际随机范围分支却直接使用原始 minAmount/maxAmount。**已复现**：1–3 钻石配方叠输出 ×10，modifiedMax=30，真实产出为 1，仍在原始 1–3 范围。修改器因此可能只增加输出空间要求，却没有增加产物。

**旧版依据**：旧 `RequirementItem.java:527-532` 的 applyModifierAmount 先掷随机数量，再调用 RecipeModifier.applyModifiers；deepCopyModified 的 :159-160 也会处理范围值。应对实际掷出的数量或范围边界应用一致的修饰规则。

### 25 [P2] 气体需求的带修改器重载没有被配方执行分派调用

**位置**：`recipe/MachineRecipe.java` 的 `canSatisfy/applyPhase`；`compat/mekanism/GasRequirement.java:161-172,201-229`。

配方只对 Item/Fluid/Energy 调带 RecipeModifiers 的重载，其余需求进入基类接口。GasRequirement 的基类重载固定转交 RecipeModifiers.EMPTY，所以通配数量/概率修改器在真实气体结算中被丢掉；parallelLimit 却会收到修改器，导致并行计算和扣账口径不一致。

**旧版依据**：`old: .../crafting/requirement/RequirementGas.java:86-98,135-143` 的 start/finish/doGasIOInternal 始终读取 context 修改器。新版确有带修改器方法，但存在方法不代表调用链已经接上。静态确认；合法 Mekanism 气体对象及真实网络未离线初始化。

### 26 [P2] 默认 Maven 构建分支漏掉已被源码硬引用的依赖

**位置**：项目根 `build.gradle:79-83` 附近的 else 分支；`gradle.properties` 的 `use_local_deps=false`。

本地分支声明 Jade、Mekanism、AE2、GuideME；默认分支只有 KubeJS、JEI、GeckoLib。源码中的对应兼容类仍参与全部编译，不会因为运行时 ModList 守卫而被 javac 跳过，因此缺少这些编译依赖。外部开发者不能依靠当前默认分支获得完整编译类路径。

本轮实测通过的是 **use_local_deps=true**；没有联网下载默认分支依赖或做干净环境重建，不能把本机离线编译成功外推为开源构建已通过。这是构建配置的静态缺陷，与旧版游戏玩法无关。

### 27 [P2] 原有整套复现器已无法编译，旧绿灯不能代表当前源码

**位置**：`_audit/m6c-verify/mmverify/ParallelCraftCheck.java:2935` 的 FactoryRig；新版 `factory/FactoryHost.java:29` 附近的 `controller()`。

重新用当前 compileJava 产物和现有 34 个复现器源码运行 javac，报 FactoryRig 没有实现 FactoryHost.controller()。本轮没有修补原复现器掩盖该结果，也没有借用旧 class 执行。

**证据**：`harness-compile.log`。当前只能给出专项探针结果，整套回归“未运行”的原因是它已经编译失败。这是验收基础设施问题，不是游戏逻辑回归的通过或失败计数。

## 已有记录但仍需所有者理解的旧版差异

以下未计入上面的 27 项新审查问题，因为项目已经把它们记为取舍/暂缓；但它们确实影响“与 1.12.2 等价”的说法。

1. 普通控制器的 failure-action reset 会使一次性输入再次支付；旧版保留已武装配方，只损失进度。代码自己在 `MachineControllerBlockEntity.java:1397-1403` 承认。decrease 回退到 0 也有同类状态风险，后续修复应统一表示“已付料但零进度”。
2. 催化剂冻结的修改器不写 NBT；重载后已消耗催化剂对应的增益会消失，现有已知限制已说明。工厂问题 05/06 与它不同，是另外两项未正确恢复的基础状态。
3. 方块结构旋转只旋转坐标，不旋转带 facing 等属性的状态；这会影响朝向敏感的结构。现有已知限制已有记录。
4. 自动搭建对未成型控制器使用 rotationSteps=0，而方块实际有 FACING；非默认方向会搭到错误方向。交接提过“未成型取 0”的实现事实，但它不能作为旧版等价性的依据。修复自动搭建时应同时对照实际控制器朝向。流体容器的模拟扣减、桶返回容器、跨维度任务归属也需要继续核查；本轮未把这些扩展为已实机确认的结论。
5. 能量跨模组通路、11 个第三方适配器、气体样板、工厂能量展示聚合等属于明确暂缓，不在本次缺陷数量里。
