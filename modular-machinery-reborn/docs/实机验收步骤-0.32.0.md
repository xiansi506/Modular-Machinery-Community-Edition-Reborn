# 实机验收步骤：波 2 + 波 3

> 这份文档是给**你在游戏里照着做**的。每条都写明：**做什么 → 该看到什么 → 如果不对，说明哪里坏了**。
>
> 覆盖 0.32.0 的两波改动：**波 2**（可配置能源单位、失败文案、升级总线 NBT）与
> **波 3**（`selector-tag` 部件标签、`dynamic-patterns` 动态结构、预览里的动态段）。
>
> ⚠️ **这两波都还没有实机验证过。** 离线复现器是 1364 PASS / 0 FAIL，但复现器测的是**纯逻辑**
> （算术、筛选、解析），它测不了「屏幕上的像素对不对」「按钮点下去有没有反应」。
> 下面这些正是复现器覆盖不到的部分。

## 0. 准备

### 0.1 放一份数据包

放在**存档**里（文档里明确说过放 `<实例>/datapacks/` 从没在游戏里确认过，别用那条路）：

```
saves/<你的存档>/datapacks/mmtest/
    pack.mcmeta
    data/mmtest/machinery/dynline.json      ← 测试机器
    data/mmtest/recipes/dynline_demo.json   ← 测试配方
```

`pack.mcmeta`：

```json
{ "pack": { "pack_format": 15, "description": "MM 实机验收" } }
```

放好之后进游戏执行 `/reload`。**这一步就该看到日志**，形如：

```
[modular_machinery_reborn] Loaded N machine definition(s) ...
```

### 0.2 测试机器：一条可加长的线

这是**用本项目自己的方块 id** 写的（旧版自带的 `assembly_line.json` 用的是旧命名空间
`modularmachinery:blockcasing@3` 那种写法，**不能直接拿来用**）。

> **这份 JSON 是怎么验证过的（如实说明）**：它里面的方块 id
> （`modular_machinery_reborn:blockcasing[casing=plain]`、`item_input_hatch`、`item_output_hatch`）
> 与**已经实机验证过**的 `example-datapack/data/modular_machinery_reborn/machinery/alloy_furnace.json`
> **逐字相同**；它的结构字段名与规则由离线复现器的同一套解析覆盖。
>
> **2026-10-14 更新（实机跑过一版之后改的）：**
>
> 1. **`faces` 改成四面都接受。** 原来只写 `["north"]`，于是「线往哪边长」取决于**你摆控制器时面朝哪边**——
>    而这件事在界面上完全看不见。实测时正卡在这里：控制器朝南，线实际往**北**长，仓口全放反了。
>    现在无论你怎么摆都能成型。
> 2. **重复段与收尾段的中间那一格是 `(0,0,0)`。** 用旧版定义的人会踩到一个已修复的缺陷：
>    解析器把「跳过原点」那条规则（**只对基座成立**）也应用到了动态段上，于是**中间那一格连同它的
>    `selector-tag` 被整个丢掉**——症状是「机器成型、仓口都在、配方也加载了，却一个端口都收集不到，
>    标签一个都没有」。现在它被保留，并有回归断言守着。
> 3. **动手搭之前先跑一次 `/mm-diagnose`**（站到控制器旁边）。它会列出结构里每个位置的标签、
>    每个仓口及其标签，以及**直接扫描世界**找到的真实仓口。`selector-tag` 在游戏里是看不见的，
>    这一步能省掉数坐标。

`data/mmtest/machinery/dynline.json`：

```json
{
  "registryname": "dynline",
  "localizedname": "Test Dynamic Line",
  "parts": [
    { "x": 0, "y": 0, "z": -1, "elements": "modular_machinery_reborn:blockcasing[casing=plain]" },
    { "x": -1, "y": 0, "z": 0, "elements": "modular_machinery_reborn:blockcasing[casing=plain]" },
    { "x": 1, "y": 0, "z": 0, "elements": "modular_machinery_reborn:blockcasing[casing=plain]" },
    { "x": 0, "y": 1, "z": 0, "elements": "modular_machinery_reborn:blockcasing[casing=plain]" }
  ],
  "dynamic-patterns": [
    {
      "name": "line",
      "faces": [ "north", "south", "east", "west" ],
      "minSize": 1,
      "maxSize": 3,
      "parts": [
        { "x": 0, "y": 0, "z": 0, "selector-tag": "input",
          "elements": [ "modular_machinery_reborn:blockcasing[casing=plain]",
                        "modular_machinery_reborn:item_input_hatch" ] },
        { "x": -1, "y": 0, "z": 0, "elements": "modular_machinery_reborn:blockcasing[casing=plain]" },
        { "x": 1, "y": 0, "z": 0, "elements": "modular_machinery_reborn:blockcasing[casing=plain]" },
        { "x": 0, "y": 1, "z": 0, "elements": "modular_machinery_reborn:blockcasing[casing=plain]" }
      ],
      "parts-end": [
        { "x": 0, "y": 0, "z": 0, "selector-tag": "output",
          "elements": [ "modular_machinery_reborn:blockcasing[casing=plain]",
                        "modular_machinery_reborn:item_output_hatch" ] },
        { "x": -1, "y": 0, "z": 0, "elements": "modular_machinery_reborn:blockcasing[casing=plain]" },
        { "x": 1, "y": 0, "z": 0, "elements": "modular_machinery_reborn:blockcasing[casing=plain]" },
        { "x": 0, "y": 1, "z": 0, "elements": "modular_machinery_reborn:blockcasing[casing=plain]" }
      ],
      "structure-size-offset-start": { "x": 0, "y": 0, "z": 1 },
      "structure-size-offset": { "x": 0, "y": 0, "z": 1 }
    }
  ]
}
```

**它在世界里的样子**（把控制器放在某处，`z` 增大 = 控制器正面朝的方向）：

```
控制器在 (0,0,0)；
基座：z=-1 一格、左右各一格、顶上一格。
动态段沿 +z 一格格接下去，每段都是「中间一格 + 左右 + 顶」的方框；
每段的中间格可以放物品输入仓；最后一段之后的收尾段中间格是输出仓的位置。
```

**为什么有两个 `selector-tag`**：重复段里标了 `input`，收尾段里标了 `output`。展开之后它们变成
`input_line_0`、`input_line_1`、`input_line_2`、`output_line_end` —— 配方就是按这些名字指认位置的。

### 0.3 测试配方

`data/mmtest/recipes/dynline_demo.json`：

```json
{
  "type": "modular_machinery_reborn:machine",
  "machine": "dynline",
  "registryName": "dynline_demo",
  "recipeTime": 40,
  "requirements": [
    { "type": "modularmachinery:item", "io-type": "input",
      "item": "minecraft:cobblestone", "amount": 1,
      "selector-tag": "input_line_1" },
    { "type": "modularmachinery:item", "io-type": "output",
      "item": "minecraft:diamond", "amount": 1,
      "selector-tag": "output_line_end" }
  ]
}
```

**注意**：输入需求带着 `"selector-tag": "input_line_1"` —— 意思是**原料必须放在第 2 段**
（段号从 0 开始）的输入仓里，别处的圆石不算。

## 1. 波 3：`selector-tag`（最值得先做的一条）

这条是波 3 的**核心用途**，也是「不测就不知道有没有用」的那一条。

### 步骤

1. 按上面的定义在世界里搭出来：控制器 + 基座 + **2 个重复段** + 1 个收尾段。
   - 第 1 段（`z=1` 那一格）放 **物品输入仓**
   - 第 2 段（`z=2` 那一格）也放 **物品输入仓**
   - 收尾段（`z=3` 那一格）放 **物品输出仓**
2. 往**第 2 段**的输入仓里放 1 个圆石。
3. 看控制器界面。

### 该看到什么

| 观察点 | 期望 |
|---|---|
| 结构是否成型 | 成型（控制器界面显示机器名 `Test Dynamic Line`） |
| **第 2 段的圆石** | 配方**开工**，输出仓里出现钻石 |
| 把圆石**只**放第 1 段 | 配方**不开工**，状态行显示 **`闲置`**，且**下一行**是 **「缺少物品输入！」** |

> **两句都要有，别只看一句。** 只显示「闲置」而下面是空的时候，文案其实已经产生了、
> 只是没能到达界面（菜单只能传整数，失败键要过一张白名单）。**2026-10-14 实机验证**时
> 这一条正是分三次才走通的：状态 → 同步 → 过网。

### 如果不对，说明什么坏了

- **只放第 1 段也开工了** → `withTag` 的筛选没生效，或者「无标签 = 全都能看到」的语义被写错了。
  这是最要紧的失败模式：说明标签形同虚设。
- **第 2 段放了也不开工** → 标签名字对不上。展开规则是 `<标签>_<模式名>_<段号>`，也就是
  `input` + `_line_` + `1` = `input_line_1`。段号从 **0** 开始。
- **状态是「没有相匹配的配方」** → 控制器把「有配方但付不起」也当成了「没有配方」。
- **状态是「闲置」但下一行是空的** → 文案没能过网（白名单），见上面的说明。

## 2. 波 3：动态结构的长度（含「16 节不该成型」）

### 步骤与期望

| # | 做什么 | 该看到什么 |
|---|---|---|
| 2.1 | 只搭**基座**（不放任何重复段） | **不成型**（`minSize: 1` 要求至少一段） |
| 2.2 | 搭 1 段 | 成型 |
| 2.3 | 加长到 **3 段**（`maxSize: 3`） | 仍成型 |
| 2.4 | 再加 1 段，变成 **4 段** | **不成型**（超过 `maxSize` 是**不匹配**，不是截断接受） |
| 2.5 | 拆掉第 4 段 | 又成型 |

### 2.4 是最有价值的一条

它验的是旧版那条最容易写错、也最难发现的规则：**太长的结构是不匹配，而不是「截断到上限接受」**。
如果 4 段仍然成型，说明长度上限形同虚设——玩家可以把线无限接长。

## 3. 波 2：失败文案（四类）

**前提**：先按第 1 节的机器搭好，但**不放料**。

| # | 场景 | 该看到的状态行 |
|---|---|---|
| 3.1 | 输入仓是空的 | **缺少物品输入！** |
| 3.2 | 给足圆石，但**输出仓塞满**圆石 | **没有足够的库存空间用于物品输出！** |
| 3.3 | 机器需要一个能源输入仓、电不够 | **缺少能量输入！** |
| 3.4 | 能源输出仓满了 | **能源输出仓已满** |

**3.2 与 3.1 必须是两句不同的话**——旧版把它们分开是有道理的：缺料和放不下是**不同的修法**。
如果两句一样，说明方向没被区分。

## 4. 波 2：可配置的能源单位

### 步骤

1. 打开 `<实例>/config/modular_machinery_reborn-common.toml`，找到：

   ```toml
   [["display.energy"]]
   Display_Energy_Type = "FE"
   ```

2. 改成 `"IC2_EU"` → **重启游戏**（不是 `/reload`，配置在启动时读）。
3. 放一个**已知电量**的能源仓（例如先让它充满），悬停看 tooltip。
4. 再改成 `"RF"` → 重启。
5. 再改成一个**错值**，比如 `"EU"`（那不是四个合法名之一）→ 重启。

### 该看到什么

| 配置 | 能源仓 tooltip 的数字 | 单位 | 仓里的实际电量 |
|---|---|---|---|
| `FE` | 原值 | FE | 不变（基准） |
| `IC2_EU` | **原来的四分之一** | EU | **不变** |
| `RF` | **原值** | RF | 不变 |
| 错值 `EU` | 退回 `FE` 的行为 | FE | 不变 |

### 三条要点

- **`IC2_EU` 下数字变成四分之一，但仓里的电量没变。** 这是「显示乘数」而不是「换算」——
  挖出来再切回 `FE`，数字应当复原成原值。验的就是这一点。
- **`RF` 下数字不变，只有单位变了。** RF 是 1:1 的标签，不是换算。
- **写错值只报一次。** 看日志应有**一行**告警说回退到 `FE`，而且**只有一行**（不是每帧一行）。

## 5. 波 3：预览界面与两个按钮

预览在**建造选择工具**（`itemconstructtool`）或 JEI 的机器预览里。

### 步骤与期望

| # | 做什么 | 该看到什么 |
|---|---|---|
| 5.1 | 打开 `dynline` 的预览 | 按钮条上**多出两个按钮**（加号、减号） |
| 5.2 | 悬停那两个按钮 | 提示里有「存在动态结构」与「当前：§aN§f」的数字 |
| 5.3 | 点**加号** | 投影**变长**；材料清单里重复段的材料**变多**；信息面板的「长/高/宽」跟着变 |
| 5.4 | 连点到上限（3） | 数字停在 3，不再变 |
| 5.5 | 点**减号**到下限（1） | 数字停在 1 |
| 5.6 | 打开一台**没有**动态结构的机器（例如 `alloy_furnace`）的预览 | 那两个按钮**不该出现** |
| 5.7 | 点那些机器的「额外信息」按钮 | **不该**有「存在动态结构。」这一行；`dynline` 的**应该有** |

### 5.1 与 5.6 是一对

它们验的是「按钮只在需要时出现」。如果 `alloy_furnace` 也出现了两个按钮，说明守卫写错了。

### 5.3 里的「材料变多」需要眼睛

「加长一节就真的要多备一节的料」这件事，离线复现器**测不了**（它要取控制器方块状态，
而离线环境没有 Forge）。所以这一条只能靠你看——这也是它被写进这份清单的原因。

## 6. 波 3：加长一节不打断正在跑的合成

这条验的是「**定格**」语义：配方的段号绑定必须在成型那一刻确定下来，不能每 tick 重新量。

### 步骤

1. 按第 1 节搭好 2 段，让配方**跑起来**（正在消耗圆石、`recipeTime` 是 40 刻 = 2 秒）。
2. **在合成跑到一半时**，去加长一段（放上第 3 段的方块）。
3. 观察这次合成。

### 该看到什么

- 正在跑的合成**不该断**，也不该换料（不该突然从另一个段的仓里拿圆石）。
- 加长之后，下一次开工时配方应当**按新的长度**重新绑定段号。

### 如果不对

如果合成在加长的那一刻断了或换了料，说明定格值没有正确存在 NBT / 没有被结构核对固定下来——
这是一个只在「有人动结构」时才出现的间歇性 bug，也是这份清单里最难自己复现的一条。

---

## 7. 波 3：存档往返

### 步骤

1. 搭好一台 2 段的 `dynline`，**存一个带圆石的输入仓在第 2 段**。
2. 退出存档 → 重新进入。

### 该看到什么

- 机器**仍然成型**（不需要重新搭）。
- 配方**仍然按第 2 段的标签**取料（第 2 段有圆石就开工，只有第 1 段有就不开工）。

### 如果不对

如果重进之后机器不成型、或者配方开始从别的段取料，说明动态结构的定格值没有活过存档。

## 8. 波 2：升级总线的 NBT 往返

这一条验的是**数据不丢**，不是「有效果」——因为读这份数据的处理器层（CraftTweaker 事件处理器）
本项目有意没有移植，所以它没有可见的效果。

### 步骤

1. 拿一个**升级载具物品**（能被升级总线识别的那个物品），用命令给它写一段自定义 NBT：

   ```
   /data modify entity @e[type=item,limit=1,sort=nearest] Item.tag."modular_machinery_reborn:upgrade_custom_data" set value {mmtest:1}
   ```

   （更省事的做法：把物品拿在手里，用 `/data modify entity @s SelectedItem.tag...`。）

2. 放进升级总线 → 存档 → 退出重进。

### 该看到什么

- 那段 NBT **仍在**。同样地，放进总线之后，物品自己的 tag 应当还在物品上。

### 为什么这条重要

一个「把它丢掉的移植版」不会报任何错，只是安静地降级玩家已有的动态升级物品。

## 9. 一份诚实的说明：这份清单里哪些是「必须做」的

如果时间有限，**按这个顺序做**（价值从高到低）：

1. **第 1 节**（`selector-tag` 真的限制了送料位置）——波 3 的整个意义在这里
2. **第 2.4 节**（16 节不该成型）——一条最容易写错、错了最难发现的规则
3. **第 3 节**（四类失败文案各说各的）——玩家最常看到的东西
4. **第 4 节**（能源单位三档 + 错值告警）——本版最容易被误认为「坏了」的改动
5. **第 5.1/5.6**（两个按钮的出现与缺席）
6. 其余各节

**任何一条不符合预期，请把那一步的实际现象（截图或日志行）发回来**——
不要只说「不对」，因为上面每一条的失败都指向不同的代码位置，而那些指向就是定位的起点。
