## 2. 已有能力：后续不要重复排期

以下功能在当前源码里已有对应实现。旧版 2026-09-29 差异报告和一些旧说明仍声称它们缺失，应以当前代码为准：

- 机器定义来源：数据包、配置目录、KubeJS；多层/任意形状结构、朝向旋转、蓝图与 `requires-blueprint`。
- 机器定义客户端同步、`dynamic-patterns` 和示例装配线。
- 仓口库存与 Forge 能力、结构端口收集、等级容量、工厂/并行控制器及配方修改器。
- KubeJS 机器定义扩展字段、升级声明与基础升级效果。
- Mekanism 化学需求/端口；气体需求的 JEI 显示与失败文案已修复。
- `color` 字段解析和方块 tint 链路已经写入当前源码。控制器、结构外壳和仓口的颜色生命周期清理及客户端刷新在 0.62.7–0.62.9 处理；**当前实机问题仍待复验**。
- Jade 仓口标题与液体容量条有专门实现；当前也待实机确认。

## 3. 移植顺序

顺序依据：先收敛已由玩家报告、且已有待部署改动的实机问题；再处理会让机器定义/配方静默偏离预期的主线差异；随后实现独立子系统与脚本面；模组兼容按真实依赖逐个推进；低优先级视觉工具最后处理。

### 第 0 步：完成 0.62.9 的实机回归（当前阻塞项）

**范围**：染色创建/清理/重绘，Jade 仓口流体显示。

**操作与验收**：

1. 使用 0.62.9 JAR 启动实例；确认机器定义设定颜色后，成型时控制器正面、模组自有结构外壳和仓立即着色。
2. 未成型或破坏控制器后，残留方块立即恢复原色；未设 `color` 的机器不被染色；其他模组方块不受影响。
3. 对 Jade 分别检查有液体、空液体仓和存化学品的流体输入仓：真实液体应显示名称与容量条；空仓不应伪报液体；化学品不应被错误画成空液体。
4. 若失败，先用 `/mm-diagnose` 记录控制器状态、机器颜色、染色方块计数和 Jade provider 读数，再改代码；保留截图与日志。

**完成条件**：逐项验收通过并记录版本、JAR 哈希、实机结果。未通过时留在本步，避免在未确认的染色/Jade 改动上叠加新行为。

### 第 1 步：修复配方语义缺口与静默失效

**范围**：以当前 `ModRecipeSerializers`、各 Requirement 实现和旧版 `RequirementType*`/`RecipePrimer` 对照。先做一张字段真值表，再逐项实现。

当前源码核实出的候选缺口：

- 输入侧物品 `chance`：当前 item input 的结算路径直接消耗需求数量，没有概率门控；输入 `minAmount`/`maxAmount` 随机消耗也未见实现。
- `fuel` 输入（旧版 `any:fuel` + `time`）和燃烧时长累计。
- 物品需求 NBT 检查/预览 NBT、耐久消耗 `consumeDurability`。
- 配方级 `priority`（影响同一台机器上配方的选择顺序）、`tooltips`、触发时间/重复触发、忽略产物空间检查、`parallelize-unaffected` 等入口。
- 普通 item/fluid/energy 需求的未知字段校验仍需逐条审查，避免字段拼错被静默吞掉。

> 上述项目要先与旧版消费者核对：旧版有些类型仅 CraftTweaker 能构造，或旧版 JSON reader 本身返回 `null`。只有旧版实际可达且有消费者的行为才纳入迁移；死代码和已明确不移植的事件层不要混入此步。

**验收**：每个字段提供旧版与新版的源码依据、正反例、网络/存档影响说明；确认物品/流体输入输出、概率、并行与失败动作没有回归。执行项目现有离线复现器和构建流程；概率、仓口消耗及 GUI/JEI 行为需要实机确认。

### 第 2 步：配方适配器子系统

**范围**：旧版 `RecipeAdapter`、`RecipeAdapterRegistry`、`RecipeAdapterAccessor`、`.adapter.json` 加载分流及 `DynamicMachineRecipeAdapter`。这不是“缺一个 JSON 字段”，而是从外部 RecipeType 读取配方、转换需求、应用修改器并接入目标机器配方列表的一整条链。

**实施约束**：先定义 1.20.1 的 adapter 接口和注册生命周期，再接一个原版机器配方类型作为最小端到端样例；不可只迁移适配器声明而没有消费者。确认配方重载时旧生成配方会被替换，避免重复堆积。

**验收**：外部配方能被发现、转换、显示在对应机器 JEI 类别、实际加工；`/reload` 后修改/删除适配器能正确更新且无重复配方。

### 第 3 步：机器定义剩余字段与结构匹配

**范围**：

- 根字段 `prefix`：接入控制器/预览等机器标题的显示。
- `hide-components-when-formed`：在成型态按旧版行为隐藏结构方块，并验证拆解/卸载时恢复。
- `controller-bounding-box`：恢复定义的 6 值包围盒行为；先追踪旧版该字段的所有读取点，确定作用对象后再实现。
- 部件 `nbt` / `preview-nbt`：当前 loader 会告警且只按 block state 匹配；评估真实需求并实现结构 NBT 匹配与预览 NBT 的区别。

**验收**：用小型数据包定义逐字段测试缺省、合法值、错误值、旋转、服务端/客户端同步、`/reload` 和旧存档行为。每项独立落地，不要把 `preview-nbt` 当作结构匹配条件。

### 第 4 步：补齐 KubeJS 对旧脚本能力的覆盖面

旧版 CraftTweaker 桥本身是**有意不移植**的，目标是通过 KubeJS 提供有价值的等价能力；当前机器定义和配方 JSON 入口不等于旧版 63 处 `@ZenClass` 能力已全部覆盖。

建议拆成两组，不整体搬运：

1. **低耦合字段**：变量集、部件 `selector-tag`、`dynamic-patterns` 等已有 JSON 支持但脚本 API 缺少的表达面。
2. **回调/脚本控制器 API**：配方生命周期回调、机器事件、升级事件及回调中可操作的控制器对象。先由项目所有者确认目标范围，再做最小 API 设计；旧版 handler 数量多，直接逐个照搬会带入旧线程/生命周期假设。

**验收**：脚本与 JSON 产生相同 `MachineDefinition`/Recipe 行为；脚本重载、删除定义和错误报告均清楚；服务器运行时确实加载 KubeJS 的部分必须实机验证。

### 第 5 步：按需移植可选模组兼容模块

当前兼容层只有 Mekanism 模块。旧版其他集成要按模块拆分，先拿到匹配的 1.20.1 API，再做依赖勘测：

1. **AE2**：旧版 ME 输入/输出总线、样板供应器及网络交互，体量最大；先挑一个玩家实际需要的子功能做可运行纵切。
2. **GregTech CEu / TConstruct / FluxNetworks / TheOneProbe**：逐个模块、可选依赖隔离；开始前取得目标版本 API，不根据 1.12.2 API 猜接口。
3. **旧 ModularMagic 魔力量集成**：按 Botania、Astral Sorcery、Nature's Aura、Blood Magic 等分别核对 1.20.1 是否仍有对应模组/API；不把多个魔法系统强塞进一个模块。
4. **IC2**：旧版集成记录需要核对目标 1.20.1 生态是否存在可支持版本；若不存在，登记为平台上不可移植，而不是留下空实现。

**验收**：未安装依赖时主模组可正常启动；安装依赖时兼容模块正确注册方块/需求/端口；专用服务器、网络同步、配方重载和 JEI 行为分别验证。

### 第 6 步：机器投影仪（低优先级）

旧版 `machine_projector` 在控制器上投射世界空间幽灵结构；当前物品仅注册，没有行为。此项工作主要是客户端世界渲染，先完成小型方向/遮挡/透明度原型再决定投入。它曾被明确延后，故排在核心配方、结构语义和实际需要的兼容模块之后。

**验收**：目标机器的动态/固定结构投影方向正确；预览不会修改世界；退出、切换目标、区块卸载和世界关闭时资源正确清理。

## 4. 明确不列为待移植项

- CraftTweaker 桥本身：目标是 KubeJS 等价入口，不增加 CraftTweaker 依赖。
- `ItemDebugStruct`：旧版未注册且实现有缺陷，已决定不移植。
- 自动把结构方块放入世界的放置器：旧版没有该功能；构造工具是选区导出器。
- 独立智能接口方块、智能接口字符串类型、真正异步工厂：项目已作出不移植/重构决定。
- 旧版 JSON reader 返回 `null` 且全仓库没有实际消费者的伪需求类型：先以源码证明为死功能，再排除。
