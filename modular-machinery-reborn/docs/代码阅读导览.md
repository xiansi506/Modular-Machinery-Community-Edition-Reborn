# 代码阅读导览（中文）

> 这份文档是给**第一次读本项目源码**的人（也就是现在的你）用的。
> 它不复述代码，只回答三个问题：**系统怎么跑起来**、**该按什么顺序读**、**想懂某个概念该看哪个文件**。

## 0. 先看这句话

**这个模组的本质是一台「数据驱动的多块机器」执行器。**

外面（数据包或 KubeJS 脚本）给一份 JSON，说「这台机器长什么样、要吃什么、产什么」；
里面（本项目）负责：解析这份 JSON → 找到并在世界里核对这个结构 → 收集结构里的端口 → 找到能跑的配方 →
检查够不够料 → 开跑 → 每 tick 结算 → 产出。

**记住这条线，读代码就不会迷路：**

```
JSON 定义           →  MachineSchema          解析 + 所有校验规则
  ↓
MachineDefinition   →  一份不可变的定义对象
  ↓
MachineRegistry     →  全局注册表（/reload 时整体替换）
  ↓
MachinePattern      →  结构：相对坐标 → 每格接受哪些方块
  ↓
BlockMatcher        →  单格的匹配规则
  ↓
HatchCollection     →  从结构里收集到的端口（物品/流体/能量/智能接口）
  ↓
MachineRecipe       →  张配方：一串 MachineRequirement
  ↓
MachineRequirement  →  单条需求：能开工吗 / 开工时消耗 / 每 tick 消耗
  ↓
FactoryEngine       →  真正干活的循环（普通机器只有一条线程）
```

## 1. 项目的「两条入口」

理解本项目的第一件事：**机器定义有两条来路，但它们共用同一套规则。**

| 来路 | 谁写的 | 触发时机 | 特点 |
|---|---|---|---|
| **数据包** | 整合包作者，写 `data/<命名空间>/machinery/*.json` | 世界加载 / `/reload` | **宽容**：未知字段只警告 |
| **KubeJS 脚本** | 服主，写 `.js` | 脚本加载 | **严格**：未知字段直接报错 |

**为什么这两条路必须共用规则**：如果一个程序化的第二入口「只挑自己关心的字段看」，脚本作者就会为**同一份
schema 拿到更差的报错**。所以规则被从 loader 里**抬出来**放进了 `MachineSchema`，两条路都调它的 `read()`
（见 `MachineSchema.java` 的类注释，写得很清楚）。

**读代码时的推论**：看到 `MachineSchema` 就该知道，**所有关于「哪些字段合法、什么值合法」的答案都在这个文件里**，
不在 `MachineLoader` 里。

## 2. 推荐的阅读顺序（5 步）

### 第 1 步：定义怎么进来（约 700 行）

| 顺序 | 文件 | 读它的理由 |
|---|---|---|
| 1 | `machine/MachineSchema.java` | **唯一的规则来源**。所有字段名、取值范围、报错文案都在这里。它的类注释讲清了「两条入口」的设计。 |
| 2 | `machine/MachineDefinition.java` | 解析完的**结果对象**：一台机器在代码里长什么样。注意它是 `record` 或不可变对象——因为 `/reload` 会整体换掉它们。 |
| 3 | `machine/MachineDirectory.java` | 从磁盘**找出**所有定义文件，并处理 `*.var.json` 变量替换。 |
| 4 | `machine/MachineLoader.java` | 把「磁盘 + 数据包 + 脚本」三层**合并**成一批定义。 |
| 5 | `machine/MachineDefinitions.java` | **暂存区**。脚本是分多次注册的，必须全部注册完才能一起生效，所以先 stage 再 `beginCycle()`。 |
| 6 | `machine/MachineRegistry.java` | **生效的注册表**。`replace()` 一次性换掉整张表；`findMatch()` 是世界里的结构匹配入口。 |

**这一段的重点**：为什么要有 `MachineDefinitions`（暂存）和 `MachineRegistry`（生效）**两个**静态表？
因为「脚本注册了一半」的状态**不能**被世界看见。读懂这一点，你就读懂了 `/reload` 为什么是原子的。

### 第 2 步：结构怎么核对（约 400 行）

| 顺序 | 文件 | 读它的理由 |
|---|---|---|
| 7 | `machine/BlockMatcher.java` | 单格的匹配规则：「这一格接受石头或圆石」。 |
| 8 | `machine/MachinePattern.java` | 整体结构：相对控制器坐标 → 每格接受什么。`matches()` 逐格核对。 |
| 9 | `machine/StructurePreview.java` | 建造预览：把结构画成红色轮廓（蓝图工具用）。 |

**这一段的重点**：结构是**相对坐标**表，所以同一份定义可以在世界里以任一朝向成型。
朝向由 `MachineRegistry.rotationStepsFor(facing)` 换算。

### 第 3 步：端口怎么收集（约 400 行）

| 顺序 | 文件 | 读它的理由 |
|---|---|---|
| 10 | `machine/HatchCollection.java` | **所有需求访问世界的唯一入口**。物品、流体、能量、智能接口都从这里问。 |
| 11 | `machine/ParallelControllerCollection.java` | 并行控制器是**另一种**收集物（它不装东西，只提供并行数）。 |
| 12 | `block/HatchKind.java` + `block/HatchTier.java` | 仓口的「种类」与「等级」两个维度。 |
| 13 | `block/MachineHatchBlockEntity.java` | 单个仓口：装物品/流体/能量的实体。 |

**这一段的重点**：`HatchCollection` 是**只读视图**——需求通过它**看**世界，但改世界要走 `apply`/`tick`。
这个区分让「能不能开工」变成**纯函数**（`canSatisfy` 被反复调用也不会改变世界）。

### 第 4 步：配方与需求（约 830 行）

| 顺序 | 文件 | 读它的理由 |
|---|---|---|
| 14 | `recipe/MachineRequirement.java` | 需求的**基类契约**，只有几个方法：`canSatisfy` / `startFailure` / `apply` / `tick`。先读它，再读子类。 |
| 15 | `recipe/ItemRequirement.java` | 最典型的一个需求实现。 |
| 16 | `recipe/FluidRequirement.java` | 对照上一条：流程一样，换了个容器。 |
| 17 | `recipe/EnergyRequirement.java` | 特殊的一个：它**按每 tick 计费**，还会缩放配方时长。 |
| 18 | `recipe/MachineRecipe.java` | 一张配方 = 一串需求 + 时间 + 产物。`canStart` / `canTick` 把它们串起来。 |
| 19 | `recipe/RecipeModifiers.java` | 升级与结构给的**加成**（并行、提速、增产）。 |
| 20 | `recipe/ModRecipeTypes.java` + `recipe/ModRecipeSerializers.java` | 配方怎么被 Minecraft 的配方系统认出来。 |

**这一段的重点**：需求的四个方法对应**生命周期的四个阶段**——
`canSatisfy`（能不能开工）→ `apply`（开工时结算）→ `tick`（每 tick）→ 结束时结算。
搞清这四个阶段的顺序，配方引擎就没有神秘感了。

### 第 5 步：执行（约 1,270 行，最难的一段）

| 顺序 | 文件 | 读它的理由 |
|---|---|---|
| 21 | `factory/FactoryThreadModel.java` | 先读这个**纯逻辑**小类：线程数怎么算。没有世界依赖，最容易懂。 |
| 22 | `factory/FactoryHost.java` | 引擎需要宿主提供什么（一个窄接口）。 |
| 23 | `factory/FactoryThread.java` | 一条线程：找配方 → 等料 → 跑 → 完成。 |
| 24 | `factory/FactoryEngine.java` | 调度所有线程。 |
| 25 | `block/MachineControllerBlockEntity.java` | **最大的文件（1,424 行）**。它把上面所有东西接起来。**建议最后读**，而且分两遍：第一遍只看 tick 流程，第二遍再看同步与 GUI。 |

## 4. 这个项目里反复出现的几个设计习惯

读懂这几个习惯，读代码会快很多：

**① 「静默失败」是本项目最大的敌人。**
项目文档里反复出现一句话：**「日志里没有报错」对这类缺陷不提供任何信息**。
例如生成式数据包少声明一个命名空间，游戏不会报错、日志不会写字，但标签**整个被忽略**。
所以你会看到大量「宁可报错也不猜」的代码，以及每条规则都带一句**「应该怎么写」**的报错文案。

**② 不可变 + 整体替换，而不是就地修改。**
`/reload` 会**换掉整张注册表**，而不是逐条更新。所以定义对象是不可变的，
「按名字查」而不是「持有对象引用」——否则一个 `/reload` 之后你手里的引用就指向上一代了。

**③ 纯函数与副作用严格分开。**
`canSatisfy` 是纯的（不改世界），`apply`/`tick` 才有副作用。
这让「能不能开工」可以被反复问、可以被并行数计算反复试探。

**④ 上游（旧版 1.12 的 Modular Machinery）的行号被当作引用写进注释。**
你会看到 `{@code TileUpgradeBus.java:275-282}` 这种写法。
**这是刻意保留的**：本项目是「重实现」，注释里标上游行号是为了让下一个人能去对照原始行为。
（同样地，本文档里所有类名、路径、上游行号都保持原样，没有译成中文。）

## 5. 关于注释本身

本项目的注释密度是 **32.9%**（8,122 行注释 / 24,656 行），而且质量很高——它写的是
**「为什么是这种做法，而不是另一种」**，不是「这行代码在做什么」。

所以读的时候建议：**先读类注释**。每个类的 Javadoc 通常都讲清了它为什么存在、
它替代了什么、以及它有什么已知的取舍。方法级注释则是补充细节。

> **中文注释正在逐文件补充**（见下节）。术语与英文标识符保持原样：类名、方法名、字段名、
> 文件路径、上游行号引用一律不译——它们是你在 IDE 里跳转和去对照旧版源码的凭据。
