## 三、这个项目的规矩（违反了会被指出）

1. **不许无据推断**：每个判断要有代码位置或实测证据。查不到就写「未查到」，不要猜。
2. **「看起来合理」不是依据**：原版可观测之处绝不自造默认值。
3. **过宽的断言等于没断言**；**假失败与真失败一样有害**；边界要由数据算出来。
4. **「日志里没有报错」不提供信息**——这类缺陷只能用运行时探针或实机 settle。
5. **看不见的状态必须能被问出来**（`/mm-diagnose` 就是为这件事存在的）。
6. **诚实报告未验证的部分**：说「已交付」必须同时说「哪些没实机验证」。
7. **中文技术文档**；术语准确，不造译名。

### 五个必须知道的坑

- **`C:\mmwork`** 是指向工作区的 ASCII junction，断言源码里的路径写死 `C:/mmwork/...`。
- **`.tmp-m6c-verify/init.gradle` 的 `keepFragments`** 是复现器类路径白名单（现有 `'mekanism'`、
  `'jade-11.13.3'`）。新增可选依赖要加进去；**不要**加 `'libs/'`。
- **`git push` 报 `Connection was reset`** 多半是 DNS 解析到不可达的 GitHub IP，不是认证；用上面的 `curloptResolve` 换一个可达 IP。Git 2.55 的 Git for Windows 只有 schannel，`-c http.sslBackend=openssl` 会直接报 Unsupported SSL backend。提交信息含引号/斜杠必须 `git commit -F <文件>`。
- **`--offline` 下不要 `clean`**——会卡在 `downloadMCMeta`（不是进程锁）。判据看 `build/libs/*.jar` 时间戳。
- **不要用 `write` 整体替换大文件**；用 `edit` 改局部，且每次 `edit` 后验证下一节标题还在。

## 九、九个教训（跨会话有效，值得带走）

1. **`PASS` 不等于「没有警告」。** 断言只看它被写来问的那件事；日志里的警告是另一份证据。
2. **涉及 API 形状的判断必须查签名。** 我凭记忆写过「1.20.1 的 `BlockColor` 拿不到位置」，
   `javap` 一看记反了。
3. **`text.contains(X)` 对「在别处加一句合法代码」是失明的。** 同一条断言被骗过两次，
   第三版按**方法体**判断才咬住。
4. **文档里的「部分完成」要对着代码核。** `craftcheck.failure.*` 写着「部分已补」，
   对表才发现 9 种键缺 2 种。
5. **文档也可能把「缺口」本身写错。** 波 6 第 1 项「光照均匀」的前提经核实不成立，整项被移除。
6. **探针自己说错话比没有探针更糟。** 「Jade 流程模拟」原来只测第一个仓，误导过一次。
7. **反复失败的机制，先做可观测性再改它。** Jade 替换器失败三次、表现完全一样，
   加计数器后才第一次能区分「没被调用」与「调用了没定位到」。
8. **多步字符串替换要考虑规则之间相互作用。** 我曾让第 6 条规则的前缀被第 1 条再匹配，生成 `../../../../`。
9. **读过还没写完的文件会骗人。** 本会话因此误判过一次「证据是坏的」。
