## 五、这个项目的规矩（**违反了会被指出**）

1. **不许无据推断。** 每个技术判断都要有代码位置或实测证据。查不到就写「未查到」，不要猜。
2. **「看起来合理」不是依据。** 原版**可观测**的地方，**绝不许自造一个「合理的」默认值或行为**。
3. **过宽的断言等于没断言。** 断言必须覆盖到会出错的那条路径；测试数据「刚好绕过出错分支」是无效的。
4. **假失败和真失败一样有害**——不要为了让检查通过而放宽它；写死的边界值会随数据增长而失效，边界要**由数据算出来**。
5. **「日志里没有报错」不提供任何信息。** 这类 bug 只能靠运行时/实机探针settle，不能靠读代码下结论。
6. **一个看不见的状态必须能被问出来。** 例如 `selector-tag` 在游戏里看不见，所以我加了 `/mm-diagnose` 命令。
7. **诚实报告未验证的部分。** 不要说「已交付」而不说「其中哪些没实机验证」。
8. **不要过度声称版本号或完成度。**
9. **中文技术文档**；术语准确，不要生造译名。

### 环境陷阱（都踩过，别重踩）

- `powershell -Command` 显示中文会乱码，但**文件字节是好的**——不要因此去"修"文件编码。
- **仓库是 LF-only**（`core.autocrlf=false`）。PowerShell 的 `Replace` 会把 CRLF 写进 LF 文件 → 用 **`edit` 工具**做多行/对行尾敏感的修改。
- PowerShell here-string 的 `Replace` 多参数会失败；**单对替换**或 `edit` 工具。
- **不要用 `write` 工具整体替换已存在的大文件**（我因此截断过一个 900 行的文件，靠 `git checkout --` 救回来）。**用 `edit` 改局部。**
- `edit` 工具替换段落时**容易把下一节的标题一起吃掉**——每次 `edit` 后 **立刻验证标题还在**（我犯过三次）。
- **`git push` 需要**：`git -c http.sslBackend=openssl -c http.version=HTTP/1.1 push origin main`。`github.com:443` **时通时不通**，重试 3–4 次；提交成功但推送失败是常见状态，**下次继续推**即可。
- 提交信息含引号/斜杠时**必须用 `git commit -F <文件>`**，不要用 `-m`（会被 PowerShell 吃掉）。
- **Gradle 离线构建**（`--offline`）可行，依赖在 `.gradle-home`。
