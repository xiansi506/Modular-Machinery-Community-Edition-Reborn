## 三、这个项目的规矩（**违反了会被指出**）

1. **不许无据推断。** 每个技术判断要有代码位置或实测证据。查不到就写「未查到」。
2. **「看起来合理」不是依据。** 原版可观测之处**绝不自造**一个「合理的」默认值。
3. **过宽的断言等于没断言**（见 §八的两次实例）。
4. **假失败与真失败一样有害**；边界要**由数据算出来**，不要写死。
5. **「日志里没有报错」不提供任何信息。** 这类缺陷只能用运行时/实机探针 settle。
6. **看不见的状态必须能被问出来**（`/mm-diagnose` 就是为这件事存在的）。
7. **诚实报告未验证的部分**——说「已交付」时必须同时说「哪些没实机验证」。
8. **中文技术文档**；术语准确，不造译名。

## 四、开发环境与命令（照抄）

```powershell
$root='C:\Users\kk07H\Desktop\模组'
$env:JAVA_HOME = 'C:\Program Files\Microsoft\jdk-17.0.11.9-hotspot'
$env:GRADLE_USER_HOME = "$root\.gradle-home"
$env:JAVA_TOOL_OPTIONS = '-Dfile.encoding=UTF-8'
$gradle = "$root\.gradle-home\wrapper\dists\gradle-8.1.1-bin\99jqdkz0zm0r14eocl2t87xca\gradle-8.1.1\bin\gradle.bat"

# 1) 离线复现器（回归；会先 jar 再跑断言）
Copy-Item "$root\_audit\m6c-verify\mmverify\*.java" "$root\.tmp-m6c-verify\mmverify\" -Force
& $gradle -p "$root\modular-machinery-reborn" -I "$root\.tmp-m6c-verify\init.gradle" m6cVerify `
    --offline --no-daemon --console=plain -Puse_local_deps=true

# 2) 出货构建（**不加 clean**：离线时 clean 会卡在 downloadMCMeta，见 §五）
& $gradle -p "$root\modular-machinery-reborn" build --offline --no-daemon --console=plain -Puse_local_deps=true

# 3) 必查 1（SRG 污染）：CREATIVE_MODE_TAB 应为 0，f_<digits>_ 应为 1
& "$env:JAVA_HOME\bin\javap.exe" -classpath "$root\modular-machinery-reborn\build\reobfJar\output.jar" `
    -c -p com.reborn.modularmachinery.block.ModBlocks | Select-String 'CREATIVE_MODE_TAB|f_\d+_'

# 4) 部署（**出货产物是 build\reobfJar\output.jar**，不是 build\libs\ 那个未 reobf 的）
Copy-Item "$root\modular-machinery-reborn\build\reobfJar\output.jar" `
    'D:\.minecraft\versions\彩虹花园\mods\modular_machinery_reborn-<版本>.jar' -Force

# 5) 推送（TLS 陷阱）
git -c http.sslBackend=openssl -c http.version=HTTP/1.1 push origin main
```

- **`C:\mmwork` 是指向工作目录的 ASCII junction**，复现器与部分断言走它（源码里的路径断言写死了
  `C:/mmwork/...`）——所以断言读的是**同一个工作区**，不是副本。
- **复现器的断言源码在 `_audit\m6c-verify\mmverify\*.java`**；改完**必须** `Copy-Item` 到
  `.tmp-m6c-verify\mmverify\` 再跑，否则跑的是旧断言。
- **以每次跑出来的 `SUMMARY: N PASS / M FAIL (T checks)` 为准**，不要引用证据文件里的旧数字
  （历史上有过被覆盖的事故）。
- **类路径白名单**在 `.tmp-m6c-verify/init.gradle` 的 `keepFragments`：新增可选依赖时要加进去
  （现有 `'mekanism'`、`'jade-11.13.3'`）。**不要**加 `'libs/'`——那会把所有 jar 都放进来。

### 环境陷阱（都踩过）

- **`git push`**：`github.com:443` 时通时不通，**重试 5–10 次**；提交成功但推送失败是常见状态，
  下次继续推即可。沙箱有时会阻止 git 建信号管道（`couldn't create signal pipe, Win32 error 5`）。
- **提交信息含引号/斜杠必须 `git commit -F <文件>`**，`-m` 会被 PowerShell 吃掉。
- **`--offline` 下不要 `clean`**：会卡在 `downloadMCMeta`（不是进程锁）。已 clean 过就先
  `Get-Process java | Stop-Process -Force` 再跑不带 clean 的 `build`；判据是 `build/libs/*.jar` 的时间戳。
- **仓库 LF-only**（`.gitattributes` 有 `* text=auto eol=lf`，`core.autocrlf=false`）：
  手工转行尾没有意义，`git add` 时 git 自己会归一化。
- **不要用 `write` 整体替换已存在的大文件**（截断过一次 900 行的文件）；用 `edit` 改局部，
  且每次 `edit` 后**立刻验证下一节标题还在**（吃掉过三次）。
- **PowerShell 的 here-string `Replace` 多参数会失败**；还要注意 `$f` 之类的变量传成对象而不是路径。
- **`Out-File` 转存复现器输出时不要用复现器自己的证据文件名**（两个进程抢同一个文件，
  会在日志里留下 `the evidence file could not be opened: FileNotFoundException`）。
- **读了还没写完的文件**：转存之后要先确认写完再 grep，否则读到上一轮的旧内容（本会话因此误判过一次）。

### 五步缺陷链（值得单独记，因为它示范了本项目的排查方式）

「化学品进不去流体输入仓」→「Jade 不显示液体」这一段里，**五个缺陷没有一个是靠读代码猜出来的**：

1. 气罐容量**借用了流体罐的总容量**（`getTankCapacity(0)` 返回 `fluid.getCapacity()`）；
2. 流体该被清掉时**没清**（方向反了）；
3. 互斥**只做了一半**（只清流体、没挡流体侧）；
4. 互斥闸门有**客户端副作用**（客户端气体罐来自旧 NBT，把装着液体的罐读成空）；
5. Jade 那一份**始终不显示**（最后靠自带 Jade 插件绕开）。

每一步都是靠 `/mm-diagnose` 的探针量出来的。**「Jade 不显示液体」那一段甚至反编译了 Jade 的
字节码**（`FluidStorageProvider` → `CommonProxy.wrapFluidStorage` → `JadeForgeUtils.fromFluidHandler`
→ `FluidView.read`）才确认它读的是标准 Forge 能力、路径本身没问题。

## 六、现在的地图（哪些地方最容易踩）

- **`compat/`**：模块自注册（`CompatModule`/`CompatRegistry`/`ModCompat`），
  在 `FMLCommonSetupEvent` 触发、`requiresModid` 兜底摘除。
  **主模组不许出现任何 Mekanism 类型**（有断言钉着：`the hatch block entity mentions no Mekanism type`）——
  兼容层要什么数据，走通用入口（`ModCompat.namedValues` / `mapPort` / `portHandlers`）。
- **`client/jei/MachineRecipeLayout.kindOf`**：需求 → 格子种类的分派。
  **`MachineRequirement.TankKind`** 是那条「物品不再是默认桶」的修正（0.58.0）。
- **`integration/jade/`**：本模组自己的 Jade 插件（`@WailaPlugin` + 客户端组件 + 替换器）。
  **插件类里不许 import 客户端类型**（Jade 在两侧都加载插件类），有断言钉着。
- **`client/MachinePartColors`**：染色处理器（`RegisterColorHandlersEvent.Block`）。
- **`command/DiagnoseCommand`**（`/mm-diagnose`）：本项目最重要的运行时工具。
  它现在有：结构标签、端口收集、气体端口、**插入尝试计数**、**闸门计数**、**Jade 提示替换器计数**、
  **逐个仓的流体能力读数**、**染色四行**（新增结构外壳计数）、配方与失败原因。
- **`machine/MachineSchema`**：定义解析。`KNOWN_ROOT_FIELDS` 是「认识的字段」白名单——
  **加了新字段必须同时加进它**，否则加载器会警告「does not know: X」（0.60.0 踩过）。
- **`machine/MachineDefinition`**：定义的不可变载体。新字段走**私有规范构造器** + `withXxx(...)`，
  不要加可变字段。

## 八、本会话学到的、值得带走的教训

1. **`PASS` 不等于「没有警告」。** 0.60.0 做完解析后断言全绿，而日志在说
   `has root field(s) this loader does not know: color`（因为字段没加进
   `KNOWN_ROOT_FIELDS`）。**断言只看它被写来问的那件事；日志里的警告是另一份证据。**
2. **涉及 API 形状的判断必须查签名，不能凭记忆。** 我凭记忆写「1.20.1 的 `BlockColor`
   拿不到方块位置」，去 `javap` 一看**记反了**（`getColor(BlockState, BlockAndTintGetter,
   BlockPos, int)` 位置在）——若没查，会写出一个不必要地复杂且更弱的方案。
3. **`text.contains(X)` 对「在别处加一句合法代码」是失明的。** `color` 那条断言前两版都被同一个
   注入骗过（① 只看 `switch` 文本存在；② 数 `return Kind.ITEM` 的次数，而 `case NONE ->
   Kind.ITEM;` 是 switch 表达式、没有 `return`，且注入本身是合法代码）。
   第三版改成**按方法体**判断才咬住（`Kind.ITEM x2, ifs x2` → 1 FAIL）。
   **要钉住「某样东西只能从一个地方出来」，就得看那个地方的形状。**
4. **文档里的「部分完成」要对着代码核，不要照抄。** `craftcheck.failure.*` 写着「部分已补」，
   我把**代码会产出的键**与**语言文件**对表，才发现 9 种键里缺了 2 种（gas 那一对）。
5. **文档也可能把「缺口」本身写错。** 波 6 第 1 项「光照均匀」的前提（旧版有环境光与光照开关）
   经核实**不成立**——那一项被移除，而不是延期。
6. **探针自己说错话比没有探针更糟。** 「Jade 流程模拟」原来只报**扫描到的第一个**流体仓
   （那是空的），看起来与界面的 32000 mB 矛盾；改成逐个仓都报之后才不误导。
7. **一个反复失败的机制，先给它做可观测性再改它。** Jade 替换器失败过三次，而三次在游戏里表现
   **完全一样**（提示毫无变化）；直到加了计数器（回调被调用次数 / 改动提示次数 / 因已处理而跳过
   次数 + 最近一次定位结果），才第一次能区分「回调没被调用」与「调用了但没定位到」。

## 九、所有者（用户）的工作习惯

- **实机反馈是主要验证手段**。要什么反馈，请**具体到「做什么 → 该看到什么 → 不对说明哪里坏了」**，
  不要让用户数坐标或猜。
- 每步做完汇报：**改了什么、依据是什么、哪些还没验证**。
- **改动要提交**（约定式提交信息，中文），网络允许时推送。
- **查不到依据就直说「未查到」**——比一个像样的猜测有用得多。
- 用户会**自己试**并回报现象（例如「第 1 条没变色」），这通常比自测更有价值：
  0.62.1 那次就是靠它发现「控制器与仓的模型根本没有 tint 层」。
