# 波 5.1 · 范围勘测：旧版脚本面 vs 本版入口

> **这份文档的用途**：波 5 的施工清单。它回答一个问题——
> **旧版脚本能写的东西，本版现在能写吗？**
>
> 项目所有者已决定（2026-10-04）：**不移植 CraftTweaker 桥本身**，交付的是它的**能力**，
> 改由既有入口（KubeJS + 数据包）提供。所以这是一张「旧版能写 → 本版怎么写」的对照表。

---

## 0. 写这份文档时守的规矩

- **每个判断都要有代码位置**。查不到就写「未查到」，不推测。
- **区分「名字像」与「真能做同一件事」**。看到两边都有 `chance` 就归为「已有」是不允许的，
  必须读两边代码确认语义相同。
- **分类只能三者之一**：**已有**（要写清**怎么写**，不能只说「有」）/ **该补** / **有意不补**（要给理由）。

## 2. 已核实的对照表（每一项都有代码位置）

### 2.1 配方格式对照

**旧版**：Java 方法链，`RecipePrimer`（80+ public 方法）
**本版**：JSON，字段集由 `recipe/ModRecipeSerializers.java` 定义（实测字段名如下）

本版支持的字段：
`registryName` / `machine` / `recipeTime` / `requirements` / `type` / `io-type` /
`item` / `fluid` / `energy` / `amount` / `chance` / `minAmount` / `maxAmount` /
`perTick` / `energyPerTick` / `max-parallelism` / `selector-tag`

本版支持的需求类型（`ModRecipeSerializers` 的 `case KIND_*`，共 **5** 个常量——
定义在 `:45-49`，switch 在 `:154-200`）：
`item` / `fluid` / `energy` / `interface_number_input` / `ingredient_array_input`

> ⚠️ **以上是 0.32.0 的坐标，已被波 5.2（0.33.0）取代。** 五个常量与那三处 `switch`/`instanceof`
> 现在都不在 `ModRecipeSerializers` 里了（那个文件从 352 行降到 163 行）：种类住在
> `recipe/RequirementTypes`（内置五种，`byName` 做两次查找），解析与过网分派在
> `recipe/MachineRequirementParser`。所以「本版支持哪些需求类型」这个问题现在的答案在
> `RequirementTypes.all()`，而**它会随装了哪些兼容模块变化**——不再是编译期固定的五种。
> 未知类型仍然**加载即报错**，而且消息里的「已注册清单」由注册表现算。

> **未知类型是「加载即报错」，而且会列出可用类型**（`:195-199`）。
> 这一点很重要：**需求类型的失败是响亮的，而需求内的未知字段不是。**

### ⚠️ 需要单独登记的缺陷：需求里的未知键被**静默忽略**

`ModRecipeSerializers` 对 item / fluid / energy 三种需求**只读自己认识的键，不校验未知键**
（全文没有 `rejectUnknownKeys`；只有 `IngredientArrayParser:92` 有）。

后果：脚本或数据包写 `priority`、`tooltips`、`time`（燃料）、`nbt`、`cancelIfPerTickFails` 之类，
**会被静默忽略、不报错**。这与本项目「响亮失败」的一贯做法相反，
而且它是 §2.3.2 那批缺口的**放大器**：写错的人不会知道自己写错了，只会觉得「没生效」。

**建议**：补需求字段时**同时**加未知键校验，或在文档里明确写出这条边界。

> 命名空间：`modularmachinery:item` 与 `modular_machinery_reborn:item` 是同一个东西
> （见 `ModRecipeSerializers.java` L27 的说明）。三种写法等价：`modular_machinery_reborn:item` /
> `modularmachinery:item` / `item`（命名空间部分被丢弃）。

**权威示例**（`example-datapack/.../power_transformer_energy_transform.json`）：

```json
{
    "type": "modular_machinery_reborn:machine",
    "machine": "transformer",
    "registryName": "transformer_energy_transform",
    "recipeTime": 1,
    "requirements": [
        { "type": "modularmachinery:energy", "io-type": "input",  "energyPerTick": 128 },
        { "type": "modularmachinery:energy", "io-type": "output", "energyPerTick": 128 }
    ]
}
```

### 2.2 旧版 59 个配方能力 × 本版（机械核对结果）

从 `RecipePrimer.java` 抽出的 59 个 `set*` / `add*` 方法，按本版是否有对应实现核对：

| 旧版能力 | 本版怎么写 | 分类 | 依据 |
|---|---|---|---|
| `addItemInput` / `addItemOutput` | `{"type":"item","io-type":"input\|output","item":…,"amount":…}` | **已有** | `ModRecipeSerializers` `case KIND_ITEM` (L155/L305) |

| `setChance` | 需求上的 `"chance"` 字段 | **已有** | 字段 `chance` 存在；**语义待与旧版逐行对照** |
| `setMinMaxAmount` | 需求上的 `"minAmount"` / `"maxAmount"` | **已有** | 两个字段都存在 |
| `setTag` | 需求上的 `"selector-tag"` | **已有**（波 3 已实机验收） | 波 3 的 `selector-tag` 层 |
| `setMaxThreads` | 机器定义上的 `max-threads` / 配方 `max-parallelism` | **已有** | `MachineSchema` 与 `MachineControllerBlockEntity` |
| `addIngredientArrayInput` | `{"type":"ingredient_array_input",…}` | **已有** | `case KIND_INGREDIENT_ARRAY_INPUT` (L192/L331) |

| `addGasInput` / `…Output` / `…PerTick…`（共 10 个方法） | — | **该补（属于 AE2/Mekanism 兼容模块）** | 本版无气体需求类型；见 `剩余项清点.md` L62 |

> ⚠️ **§2.2 里标着「语义待对照」的那几行，勘测已经查出答案了，而且答案不好：**
>
> - **`chance` 名字像、语义不同，而且是静默失效。** 旧版输入侧的 `chance` 是「**按概率消耗**」
>   （`RequirementItem:253-255`）；本版对 item 输入**解析后直接丢弃**（`ModRecipeSerializers:160-167`），
>   对 fluid 输入存了但 `modifiedChance` 恒为 1.0（`FluidRequirement:70-75`）。
>   也就是说**照旧版写法写一个带 chance 的输入需求，本版会接受、不报错、而且完全不生效**。
>   这一类是「看起来能写、实际效果不同」的最坏形态，详见 §2.3.2。
> - **`setMinMaxAmount` 在输出侧确实已有，在输入侧被明确拒绝**（旧版 `RequirementItem:332` 真会随机消耗），
>   见 §2.3.3 的最后一行的建议复核项。
> - **`setChance` 的取值域**（0..1 还是 0..100）与「产出概率 / 消耗概率」的取舍，
>   仍**没有**逐行核对——它并入了上面的结论里，属于待补的功课。

#### 2.3.5 该补 —— G5 / G6 / G7

- **G5 需求类型注册表**：旧版是 `RegistriesMM.REQUIREMENT_TYPE_REGISTRY`（`RecipeModifierBuilder:70` 从表里取类型）；
  本版曾是 5 个常量 + 三处 switch/instanceof。`剩余项实施顺序.md:221-222` 已把它列为**波 5.2 交付物**
  → **✅ 已于 0.33.0 交付**：`recipe/RequirementType`（接口，含 JSON 与线上两端的读写）、
  `recipe/RequirementTypes`（注册表，内置五种）、`recipe/MachineRequirementParser`（分派，可离机驱动）、
  `compat/CompatModule` + `compat/CompatRegistry` + `compat/ModCompat`（模块自注册，
  `FMLCommonSetupEvent` 触发，`requiresModid` 兜底摘除）。**一处既有行为被有意改动**：
  需求的种类字符串在**网络包**里从裸 path（`item`）改成全限定 id（`modular_machinery_reborn:item`）——
  不改的话，一个按自己 modid 注册的兼容种类**发得出去、读不回来**（单机正常、联机报「未知需求类型」）。
  JSON 侧的三种写法（`item` / `modularmachinery:item` / `modular_machinery_reborn:item`）不变。
- **G6 适配器子系统**：**判断——`RecipeAdapterBuilder` 不是「只有 CT 可达的死类型」**。
  同一套 accessor 有 JSON 入口：`RecipeLoader:106-121` 读 `*.adapter.json`（`FileType.ADAPTER:157`），
  `RecipeAdapterAccessor:61` 也能从 builder 构造。本版 `adapter` grep 零命中（`已知限制.md:39` 已登记为缺口）
  → **该补的是子系统**；CT 那个类本身**有意不补**（有 JSON 入口就够）。
- **G7 升级侧两块已排期的**：物品能力层（旧 `CapabilityUpgrade`；`UpgradeTarget:15-19` 注释自认
  「deliberately absent」）与把升级写进某 ItemStack（旧 `MachineUpgradeHelper.addUpgradeToIItemStack:62-80`）、
  总线侧自定义 NBT（旧 `IMachineController:140-149`）→ `剩余项实施顺序.md:89-99`（波 2 轨 A）已排期。

#### 2.3.7 已有（写法已核实）

**关键结构差异（读对照表前必须先看懂）**：本版**配方**不是「用 KubeJS 方法写」，而是
**在 JS 里原样写本模组的 JSON 对象**：

```js
event.recipes.modular_machinery_reborn.machine({ /* 与数据包 JSON 同形 */ })
```

用 `javap` 确认它是**空的 RecipeSchema 子类**（只有 `SCHEMA` 字段与默认构造器）→ **无自带键、无 schema 校验**，

`machine` / `registryName` / `recipeTime` / `requirements` / `type` / `io-type` / `item` / `fluid` /
`energy` + `energyPerTick` / `amount` / `chance`(输出) / `minAmount` + `maxAmount`(输出) /
`perTick`(fluid) / `max-parallelism` / `selector-tag`，
以及任务清单外的 `interface` + `value` / `minValue` / `maxValue`（`InterfaceNumberInputParser:48-74`）
与 `items[]`（`IngredientArrayParser:83-125`）。

- **每 tick 流体**：`fluid` + `"perTick": true`（`ModRecipeSerializers:182-183`，`FluidRequirement:122-146`）
  ——与旧 `addFluidPerTickInput/Output:504-544` **语义一致**（非 perTick 的开工/完工一次性结算见 `FluidRequirement:13-16`）。
- **每 tick 能源**：`energy` + `energyPerTick` + `io-type`（`:185-188`）。
- **机器定义 11 个扩展字段 + `parts`/`elements`/`block`/`register`**：`MachineBuilderJS:68-486` 逐条对得上旧
  `MachineBuilder`（并行 3 + 工厂 4 + `failure-action`/`requires-blueprint` + `modifiers`/`smart-interfaces`/`core-threads`），
  校验共用 `MachineSchema`。
- **升级声明面**：**已有，但走数据包/配置目录 JSON，不经 KubeJS**——
  `data/<ns>/upgrade/<name>.json` 与 `<name>.item.json`（`UpgradeLoader:55-57,183-277,309-337`，
  已知字段 `:297-301`：`name`/`localizedname`/`level`/`max-stack`/`dynamic`/`compatible-machines`/

  （`UpgradeEffects:43-45,132-172`）。

## 3. 结论与建议顺序

### 3.1 真缺口只有两块

1. **「脚本回调 + 回调里能操作的控制器 API」整套**（G1）：
   配方 12 个处理器 / 机器 7 个 / 升级 15 个 / 4 个函数式接口 / `IMachineController` 约 35 个成员。
2. **配方与机器定义侧一批没有 JSON 字段的旧 CT 能力**（G2 + G3 + G4）：
   `priority`、`tooltips`、`triggerTime`/`Repeatable`、`ignoreOutputCheck`、`parallelize-unaffected`、
   输入 `chance`、物品 NBT、`fuel`、`randomItemOutput`、配方级 `maxThreads`、
   脚本 patch 已注册机器、per-part `selector-tag`/`nbt`、`dynamic-patterns` 脚本入口。

### 3.2 建议顺序

1. **先拍板 G1 的立场**（`移植方案-v2.md:326` 的「不实现」是否作废）。**在拍板前 G1 不排期。**
2. 若补 G1：先做「**回调基础设施 + `IMachineController` 等价物**」——因为 G3 的输入 `chance`、
   物品 NBT、itemChecker 与升级的 15 个处理器**都挂在它上面**。
3. **波 5.2 的第一件事（无争议）**：把需求类型从「5 个常量 + switch」变成**可注册表**
   （`ModRecipeSerializers:45-49` / `:154-200`）。这也是兼容层往注册表里加需求类型的前提。
   → **✅ 0.33.0 已交付**（见 §3.3 G5 那一条；三处 switch/instanceof 都在这一波消失了）。
4. 再做 G2 里**纯字段**的那批（`priority` / `tooltips` / `parallelize-unaffected` / 配方级 `maxThreads` /
   per-part `selector-tag` / `dynamic-patterns` 脚本入口）——**全部低价、不影响引擎结构**。
5. `fuel`、`consumeDurability`、输入区间、`randomItemOutput`：**先登记**，再按所有者意见取舍。
6. `catalyst` / GeckoLib / 注册新方块 / 取消 per-tick 标记：**保持「有意不补」**。

#### 问题 1（最关键，且是「记录冲突」而不是「技术未知」）：G1 那套回调要不要补？

#### 问题 2：`priority` 不只是少个字段，而是**行为不同**

旧版按优先级分层选取配方（`RecipeRegistry:170-183` 的 `TreeMap<Integer, …>`），

**要不要把「优先级选取」这个行为也补上？**（附：旧版排序方向「小者先还是大者先」本次未核对）

#### 问题 3：`fuel` 与 `consumeDurability` 目前**连缺口清单都没进**

- `fuel`（旧 `addFuelItemInput:668-672`）：本版 `recipe/` 包零命中、JEI 层自认缺该字段
  （`MachineRecipeText:30`），但 `已知限制.md` / `剩余项清点.md` **都没登记它**。
- `consumeDurability`（旧 `RecipePrimer:198-220`）：这是**唯一「引擎里连字段都没有」的功能性能力**。
  现有文档把它记在 D7/D18「不是缺口」名下，**但那条理由的前提是「旧版 JSON 无此入口」**，
  而实测**旧版 CT 真能写、引擎真会扣耐久**——按新口径这条前提不成立。

#### 问题 4（低优先，但需要登记）：GeckoLib 没有决策记录

本版 `build.gradle` 无 geckolib 依赖（`:28-42`），客户端模型层不存在，`prefix` 也在未实现字段里
（`MachineSchema:636`）。**「不做」看起来是对的，但仓库里查不到所有者拍过这句话** → 建议登记。

#### 问题 5（低优先）：`MultiBlockModifierBuilder` 的「不做」理由有一半已过时

`machine/MachineModifier:20-27` 的注释说 `MultiBlockModifierReplacement`「新数据模型没有对应物」，
但它给的理由之一是「`dynamic-patterns` 仍未实现」——**0.32.0 已经实现了** → 建议低优先复核。
（另：旧类自身未完成——`descriptions` 永远为空、无名 `newBuilder()` 给 `null`。）
