## 1. 一句话：1.20.1 没有「气体 API」，只有「化学 API」，气体是其中一味

旧版的 `mekanism.api.gas.*` 在 1.20.1 已被重写成一套**统一的 chemical 体系**，
`Gas` 只是四种 `Chemical` 之一：

```
Chemical<C>                        （抽象基类，四种味道都继承它）
├── Gas          ChemicalType.GAS
├── InfuseType   ChemicalType.INFUSION
├── Pigment      ChemicalType.PIGMENT
└── Slurry       ChemicalType.SLURRY

ChemicalStack<C>                    （抽象；amount 是 long）
├── GasStack      extends ChemicalStack<Gas>
├── InfusionStack
├── PigmentStack
└── SlurryStack
```

`IChemicalHandler<C, S>` 是统一的 handler；每种味道另有一个窄化别名
（`IGasHandler extends IChemicalHandler<Gas, GasStack>`、`IInfusionHandler`、…）。

## 2. 逐条对照（旧版 1.12.2 → 本版 1.20.1）

| 旧版（1.12.2） | 1.20.1 实测 | 差异的性质 |
|---|---|---|
| `mekanism.api.gas.Gas` | `mekanism.api.chemical.gas.Gas extends Chemical<Gas>` | 改名 + 泛型化 |
| `mekanism.api.gas.GasStack`，`amount` 是 `int` | `mekanism.api.chemical.gas.GasStack`，`getAmount()` 是 **`long`** | **类型变了**：所有 `int amount` 要重算 |
| `GasRegistry.getGas(String)` | `MekanismAPI.gasRegistry()` → `IForgeRegistry<Gas>`，键是 **`ResourceLocation`** | **见 §3，这是本波最硬的差异** |
| `IGasHandler`（`receiveGas`/`drawGas`/`canReceiveGas`/`getTankInfo`） | `IChemicalHandler<C,S>`：`getTanks`/`getChemicalInTank`/`setChemicalInTank`/`getTankCapacity`/`isValid`/`insertChemical`/`extractChemical`，配 `Action.EXECUTE\|SIMULATE` | **完全不同的接口形状**（旧的「边收边扣」变成「先 SIMULATE 再 EXECUTE」） |
| `IExtendedGasHandler extends IGasHandler`（本模组自己加的 `drawGas(GasStack, boolean)`） | **不需要**：`IChemicalHandler.extractChemical(STACK, Action)` 自带「按指定栈抽取」 | 本模组自有扩展可以整块丢掉 |
| `GasStack.writeToPacket` / `GasStack.readFromPacket` | `ChemicalStack.writeToPacket(FriendlyByteBuf)`（**父类**）+ `GasStack.readFromPacket(FriendlyByteBuf)`（静态） | 形状不变，照抄即可 |
| `HybridGasTank extends HybridTank implements IExtendedGasHandler`（198 行） | 待定，见 §4 | 结构可沿用，接口要重写 |
| `GasRegistry.getGas` 找不到时报 `JsonParseException` | 同款（注册表 `getValue(null-id)` 返回 null） | 照抄 |
| `RequirementTypeGas.requiresModid()` 返回 `"mekanism"` | 同款，走本版 `RequirementType.requiresModid()` | 已在波 5.2 备好 |

### 2.1 旧版 `gas` 需求的语义（逐行读出的，本模块要照抄的部分）

`RequirementTypeGas.createRequirement`（`:39-74`）：

- **必填** `gas`（字符串）与 `amount`（数字）；
- `amount` 被 `Math.max(0, amount)` **夹到非负**（旧版是静默夹，本版照「响亮」惯例应改为报错，见 §5）；
- 可选 `chance`，**只有在 `0 <= chance <= 1` 时才采用**，否则**静默丢弃**（同样应按响亮惯例改为报错）；
- 未知气体名 → `JsonParseException("The gas specified in the 'gas'-entry (…) doesn't exist!")`。

`RequirementGas`（`:81-152`）：

- `startCrafting` 只在 `actionType == INPUT` 时扣，且要先过 `chance.canWork(...)`；
- `finishCrafting` 只在 `actionType == OUTPUT` 时产出，同样过 chance；
- **`canStartCrafting` 对输入和输出都会模拟一次**（`doGasIO`），失败键：
  `craftcheck.failure.gas.input` / `craftcheck.failure.gas.output.space`；
- 并行上限按 `totalIO / required` 算，与 item/fluid 同一套。

`RequirementGasPerTick`（`:69-72`）：`canStartCrafting` + `doIOTick` 都走 `doGasIO`，
即**每 tick 结算一次**——与本版 `fluid` + `"perTick": true` 的表达完全同构。

> **结论：`gas` / `gas_pertick` 在本版应当就是两个需求类型，形状与 `fluid` 两族一一对应**，
> 差别只有「借哪套 handler 读液位」这一件事。这也是旧版自己的形状。

## 3. ⚠️ 最硬的差异：气体名从「无命名空间的字符串」变成「ResourceLocation」

- 旧版：`GasRegistry.getGas("oxygen")` —— 配方里写 `"gas": "oxygen"`，**没有命名空间**。
- 1.20.1：`MekanismAPI.gasRegistry()` 是 **Forge 注册表**，键是 `ResourceLocation`，
  所以配方必须写 `"gas": "mekanism:oxygen"` 这种形式。

**后果**：**旧版的气体配方文件不能照旧读。** 这不是「实现得不够好」，而是 1.20.1 的注册表身份就是
全限定的——本项目的 `fluid` 需求也是同一个形状（对 `ForgeRegistries.FLUIDS` 取 `ResourceLocation`）。
所以要把「旧文件照旧可读」那句话从本模块的承诺里**划掉**，改为：

- 写错 → **加载即报错**，消息说清「旧版写的是无命名空间的 `oxygen`，本版要写 `mekanism:oxygen`」。

> **未查到（如实登记）**：Mekanism 1.20.1 里气体注册键的**确切拼写**
> （是 `mekanism:oxygen` 还是 `mekanism:oxygen_gas`，以及是否有 `mekanism:gas/...` 之类的分组）
> ——**本机无法离线枚举一个 Forge 注册表的内容**。这一条必须实机用 `/mm-diagnose` 之类的探针或
> JEI 里的气体提示确认，**我不猜**（规矩 1、2）。
> 因此实现里**不做任何名字映射**：不认识就报错，绝不「看起来像就当成它」。

## 4. 化学端口：旧版本就没有新方块

**这是本轮最重要的一条好消息。** 勘测旧源码发现，旧版的气体端口**不是新方块**：

- `HybridGasTank extends HybridTank implements IExtendedGasHandler`（198 行）——它挂在**已有的**流体仓上，
  一个罐子要么装流体、要么装气体（`setFluid` / `setGas` 互斥）；
- 宿主是 `TileFluidTank`（8 处引用）与 `GuiContainerFluidHatch`（5 处），全部用
  `@Optional.Method(modid = "mekanism")` 标注。

也就是说旧版是**「流体仓顺带能装气体」**，而不是「另做一套气体仓」。这条路正好绕开
本项目的 **D8**（方块只能在 mod 构造期注册、注册表随后冻结），所以：

> **1.20.1 这一侧的正确形状 = 给已有的流体仓加一个可选的气体能力**
> （`IChemicalHandler` 的 `LazyOptional` + 端口收集时多收一类），**不新增方块、不新增仓种类**。

**规模**（旧版实测，供估工）：

| 类 | 行数 | 说明 |
|---|---|---|
| `HybridGasTank` | 198 | 罐体本身（读写 NBT、receive/draw） |
| `MultiGasTank` | 324 | 多方块罐（ME 总线用，本轮不需要） |
| `TileFluidTank`（改动） | — | 挂气体的宿主 |
| `HybridFluidUtils` 里的气体分支 | — | 模拟/执行的公共算术 |

## 5. 建模决定：`modifierTarget()` 用哪一个枚举项？

本版 `RecipeModifier.Target` 是**闭枚举**（`ITEM`/`FLUID`/`ENERGY`/`DURATION`/`ALL`），
波 5.2 已把它登记为「本轮保持闭枚举」的待改项。气体没有自己的枚举项，所以只有两个选择：

- 选具体项（比如 `FLUID`）→ **「xN 流体产出」这类修改器会错误地作用到气体上，而且不报错**；
- 选 **`ALL`** → 只有通配修改器（`"target": "*"`）能碰到气体。

**决定：用 `ALL`。** 已实测 `RecipeModifier.matches`（`:209-224`）的语义——
`target == ALL` 对所有 `requirementTarget` 都返回 true，所以「结构修改器写了 `*` 就该作用到所有需求」
这条直觉仍然成立；而写 `fluid` 的修改器**碰不到气体**，这是可解释的。

> 代价如实说：旧版气体**能**被 `"target": "gas"`（或注册表里的气体类型）的修改器精确命中，
> 本版不行。这属于波 5.2 那个「闭枚举」决定的直接后果，不是本模块新引入的缺陷。
> 复现器里会有一条断言把这个现状钉住（它将来变红，就是那个改动该做的信号）。

`gas_pertick` 同样用 `ALL`。

## 6. 离线能证 / 只能实机（先划清楚，免得事后声称）

**必须实机（离线无论如何证不了）**：

- **气体的注册键拼写**（§3）——Forge 注册表内容，离线拿不到；

**已实测：这套 API 在离线环境里的边界是二分的。** 用一个一次性探针
（`_audit/m6c-verify/probe/MekProbe.java`，非交付物）对 Mekanism 的类逐项打过，结论如下；
后来在**复现器**里（它比裸探针多调了一次 `Bootstrap.bootStrap()`）又测出第二种形态：

| 类 / 调用 | 离线结果 |
|---|---|
| `ChemicalType.values()` | ✅ 4 个值（GAS/INFUSION/PIGMENT/SLURRY），`ChemicalType.GAS.getSerializedName()` = `"gas"` |
| `Action.SIMULATE` / `Action.EXECUTE` | ✅ `simulate()=false` / `execute()=true` |
| `IGasHandler` 接口 | ✅ 可加载 |
| `ChemicalStack.writeToPacket` / `GasStack.readFromPacket` | ✅ 方法存在（形状合规） |
| `MekanismAPI.gasRegistry()`（**裸进程，未 bootstrap**） | ❌ `ExceptionInInitializerError`，根因 `IllegalArgumentException: Not bootstrapped`（`MekanismAPI.java:49` 的 `registryKey`） |
| `MekanismAPI.gasRegistry()`（**复现器里，已 bootstrap**） | ⚠️ **返回 `null`**（Forge 注册表尚未接上），于是 `getValue` 是一个 NPE |
| `GasStack.<clinit>` | ❌ 它要 `MekanismAPI.EMPTY_GAS`，所以上一条失败时整个类都建不起来 |

**于是离线能证的是「不碰注册表」的那一半**：注册与摘除、种类身份、`requiresModid`、以及**全部字段校验**
（amount 的缺失/非数字/<1、chance 的非数字/越界、gas 的缺失/非字符串/空/非法 id）。

**为此实现里做了一件有意的安排**：`GasHandler.read` **先校验本需求自己的字段，最后才去查注册表**
（`MekanismModule.GasHandler#read`）。若顺序反过来，一条 amount 写错的配方会报「气体不认识」，
把人指到完全错误的字段上——而且那会让上面那一整批字段断言全都失去意义（它们会因为错误的原因通过）。
这条顺序不是风格，它是这一批断言能存在的原因。

**构造一个真实的 `GasStack`**：`ChemicalStack` 内部持有
`Holder.Reference<CHEMICAL> chemicalDelegate`（`ChemicalStack` 字段实测），而 `Holder.Reference` 来自注册表。
所以「拿一个真气体建栈」这条路**只在游戏里走得通**——本模块的过网往返因此**只能实机验**。

**化学端口的实机行为**：仓能不能装气体、能不能过网、机器能不能开工。

### 端口为什么是「通用机制」而不是「主模组认识气体」

主模组**一个 Mekanism 类型都没出现**（复现器里有一条源码断言钉住这一点）。理由不是洁癖：
`MachineHatchBlockEntity` 每个世界都会被加载，**包括没装 Mekanism 的进程**；它的
`getCapability` 是每次能力查询都会走的路，那里出现一次 `IGasHandler` 就意味着没装 Mekanism 的玩家
一放机器就 `NoClassDefFoundError`。所以：

| 角色 | 谁 |
|---|---|
| 知道「气体是什么能力」 | `compat/mekanism/MekanismAnchor`（只在模块注册后被加载） |
| 只认识「有个模块要认领这个能力」 | `compat/BlockEntityPortMapper` + `ModCompat.mapPort` |
| 提供端口给配方引擎 | `ModCompat.portHandlers` → `HatchCollection.Builder.gasPorts` |

桥必须**同时**实现三条路，缺一条就有一半永远不工作，而那在离线环境里是**完全静默**的：

1. `map`（能力查询）——少它，Mekanism 的管道永远问不到这个仓；
2. `handlers`（端口收集）——少它，配方永远看不到气体端口；
3. `save` / `load`（持久化）——少它，装了气体的仓重载后清空。

复现器对三条都有断言，且对第 2 条做过故障注入（见下 §10）。

### 一个**实测出来的**设计结论：能力对象必须懒取

第一版把 `Capabilities.GAS_HANDLER` 缓存在模块里、在 `FMLCommonSetupEvent` 里赋值。那**可能读到 null**：
`mods.toml` 的 `ordering="AFTER"` 只保证 Mekanism 的**构造**在前，不保证它的静态初始化已经跑到
建立能力对象那一步。缓存一个当时还可能是 null 的值，症状是**气体端口永远不工作而日志里什么都没**。
现在改成在能力查询发生时才读（那时早已就绪）。

同时**删掉了「模块自己注册能力」那套东西**：Forge 的能力是**按类型**的身份对象，而 Mekanism 已经用
`@AutoRegisterCapability` 声明了 `IGasHandler`——本模组必须**读**那一个，注册第二个只会得到另一个身份，
两边的查询永远匹配不上。这一点写进了 `MekanismModule#registerCapabilities` 的注释（它现在是空的，
并说明了为什么应当是空的）。
